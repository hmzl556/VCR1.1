## 一句话定位

**遥控器是机顶盒的"4G 上网卡"**：机顶盒（没网或广电专网）把收视行为数据（换台、观看时长等）经 BLE 小包发给遥控器，遥控器汇聚、加密后经 Cat.1 UDP 发到云端大数据平台（数据采集服务器 106.53.179.53:8888）。这就是广电"收视率统计"系统的数据来源——用户看了什么台、看了多久，都从遥控器上报。

## 通俗类比：代收快递的转运站

```
STB（发货方）: 把一个大包裹拆成 ≤128B 的小包，标上"第N件/共几件"，经 BLE 发给遥控器
遥控器（转运站）: 收货验货(CRC/去重) → 拼回大包 → 套 0x6868 信封 → AES 加密 → Cat.1 UDP 寄出
云端（收货方）: 回 Tag11 回执（收没收到 + 下发采集策略 + OTA 版本通知）
```

## 三层协议栈（吃透这个就能答一切 CAT1 问题）

### 第 1 层：BLE RC 服务（STB ↔ 遥控器，doc/4G遥控器交互数据接口-V0.3.md）
- 基础服务 UUID `19ee51a4-...-000`，**5 个特征**：
  - **RC-READ**（61B，只读）：设备信息（编码/区划码/型号/版本/MAC），STB 连接后先读它验身份；
  - **RC-CONF**（16B，写）：STB 下发 4G 传输配置（最大重传、重试间隔、休眠延迟）；
  - **RC-TRANS**（≤128B，写）：**主业务通道**——STB 的大包拆成 ≤112B 有效载荷的小包，带 PackHeader 0x55AA + PackIndex(4B) + SubPackIndex(1B，**倒序**，0x00=最后一片) + CRC16；
  - **RC-STATUS**（14B，读+notify+indicate）：遥控器回状态 IDLE→READY→BUSY→DONE/ERROR + 结果码（CRC_ERROR/DUPLICATE/BUSY_REJECT/NET_ERROR…）+ 云端策略；
  - **RC-KEY-NOTIFY**（4B，notify）：HID 上报键值的同时镜像一份（业务同步，不替代 HID）。
- **状态机**：上电 IDLE → STB 写 CONFIG 合法 → READY → 收到 Sub=0 尾片 → BUSY（开始 4G 上传）→ 成功 DONE / 失败 ERROR。**BUSY 期间禁止进休眠**。
- **可靠性设计**：按 PackIndex+SubPackIndex 去重（断线重连后 STB 会重发）；重复包回 DUPLICATE；BUSY 中收到新包回 BUSY_REJECT；PackIndex 到 0xFFFFFFFE 回卷（回卷后允许 0 的例外判重）。

### 第 2 层：UDP 数据帧（遥控器 ↔ 云端，5G 数据采集接口文档）
- **0x6868 帧**：`68 68` + 版本 0x10 + **BCD 时间 6B**(YYMMDDHHMMSS) + **MID 2B**（每发一帧 +1，云端以相同 MID 回响应）+ 设备 MAC 6B + 长度 + **TLV 数据域** + 累加和校验 1B + `0x16` 尾；
- **TLV 编码**：Tag(1B) + Length(2B) + DataID(1B) + 值；Tag 0x01=终端状态、0x02=机顶盒信息、0x03~0x09=各类收视行为（登录/直播/时移/回看/点播/页面/广告）、**0x10=按键采集**、**0x11=云端响应**（下发：是否开启按键采集/上报间隔/每次条数/**软件版本号+总包数 → OTA 触发**）；
- **AES-128-ECB + PKCS5Padding** 加密数据域（tiny-AES-c 开源库，静态 RAM）；
- **MID 在出队时才写入**：排队中被丢弃的帧不占号，云端按 MID 判重/排序不会跳号。

### 第 3 层：AT 指令（遥控器 ↔ Cat.1 模组，利尔达 NT26）
- USART2（115200，PB4/PB5）接模组；**RX 用 DMA_CH2 循环环形缓冲**（CH1 让给语音 ADC），TX 轮询发送（等待期间 pump 处理下行 URC，防丢 +ECSONMI）；
- **22 阶段 setup 状态机**：CSCON/CEREG/CSQ/ICCID/ECFREQ 诊断 → **CCLK? 网络时间锚定** → **CGATT? 轮询附着**（2s 间隔、60s 总超时）→ CGPADDR → ECSOCL 关残留 → **ECSOCR 建 UDP socket** → ECSONMI 开下行 URC；
- 发数据：`AT+ECSOST=sock,ip,port,len,HEX大写`；收数据：模组发 `+ECSONMI: sock,len` URC → 遥控器 `AT+ECSORF=sock,1024` 主动读。

## 与低功耗的联动（这俩模块咬合的地方，面试好讲）

**"事务完成即断电、有数据才上电"**：
- LTE_EN（PB2）经 MOSFET Q1 控制模组电源，平时模组**完全断电**；
- 有 RC-TRANS 待发 → 上电 → 2s boot 等待 → 22 阶段 setup → 发帧 → 等 Tag11 回执 → **立刻断电**；
- 连续 3 次发送失败 / 连续 3 次上行后无下行 → 断电重启（比软件重建更省电更干净）；
- 断电时把 PB4（USART2 TX）配成**输出低**——否则 TX 空闲高电平经模组 ESD 二极管给未上电的 VBAT 轨充电（就是你低功耗笔记里的 500µA 故事，这里也有份）。

## 关键工程细节（按需取用，都是好故事）

1. **脏行抢救解析**：UART 偶发丢字节导致 ECSORF 数据行缺引号/hex 长度不符——按 ECSONMI 声明长度搜 "6868" 抢救，声明与 hex 不一致时信任 hex 截取，**半包一律拒绝**（宁可重来不吞脏数据）；
2. **URC 处理**：`+` 开头的行先按 URC 捕获，判定不是 ECSONMI/CSCON 就把吃掉的字节**吐回**应答行（spill 机制）；ECSONMI 排队（pending + extra 计数上限 8）；
3. **CME 406 防死循环**：socket 失效 → 置事件 → 立即软重建；超时未拿 OK 时清 ECSONMI pending 防残留 URC 引发连环 406；
4. **队列压力**（git 历史里"已解决队列压力"就是它）：发送队列深度仅 2；**RC-TRANS 优先，满时丢 Tag10 腾位**（按键采集数据可丢，收视数据不能丢）；BUSY 孤儿 8s 强制 ERROR 防 STB 卡死；
5. **时间同步双锚点**：主锚点 AT+CCLK?（模组网络时间），备锚点 Tag11 帧头时间（按 +8 时区换算）；锚点 + 单调 ms 计数器推算当前时间，转 BCD 写入帧头；软重建不清锚点（墙钟不丢）；
6. **共享缓冲保护**：下行接收缓冲同时兼做发送缓冲，靠 recv_allow 开关在队列操作窗口禁止 ECSORF 写入；
7. **OTA 与业务互斥**：OTA 会话期间拒绝 RC-TRANS、丢弃 Tag10、暂停按键采集。

## 面试自测题

1. 为什么遥控器要挂 Cat.1 模组？整个系统的业务闭环是什么？（收视数据采集 → 云端汇聚 → 收视率统计）
2. STB 的大包为什么拆成 ≤128B 小包？SubPackIndex 为什么倒序？（BLE Write 单包 ATT_MTU 限制；0x00=尾片是协议约定，收齐尾片即完成）
3. 0x6868 帧的 MID 干什么？为什么出队时才写？
4. AES-128-ECB+PKCS5 的特点？为什么嵌入式环境选它？（简单、代码小、静态 RAM；ECB 对短帧够用）
5. 模组上电/断电策略？"事务完成即断电"省了什么？
6. AT 状态机怎么处理 URC？（主状态机 + URC 行分类 + pending 队列）
7. 时间同步为什么两个锚点？CCLK 锚点为什么不能被覆盖？
8. UART 丢字节了怎么办？（脏行抢救策略）
9. 队列深度 2 够用吗？Tag10 为什么可丢？
10. BUSY 孤儿是什么问题？怎么防？
11. BLE 和 CAT1 为什么要串行化？（单核，ECSORF 收包窗口内发 BLE notify 会拖垮 UART 消费——你写的 HID 延后机制就是这个）
12. Cat.1 / NB-IoT / 4G 的区别？为什么选 Cat.1？（速率/功耗/成本折中；模组 NT26 是 NB-IoT 指令兼容系列）

## 与硬件岗的关联点

- CAT1 电源开关电路：LTE_EN(PB2) → Q1 MOSFET 控制模组 VBAT（原理图 _sch_r4_cat1.png）；
- 电平转换：Q3/R30 电路（模组 IO 电平与 MCU 3.3V 之间的适配）；
- PB4 对未上电模组的 ESD 灌电问题（与低功耗笔记同一故事）；
- VLTE 分压检测（PB6 ADC 监测模组电源轨）；
- LTE 天线/SIM 卡电路（ICCID 诊断读取）。
