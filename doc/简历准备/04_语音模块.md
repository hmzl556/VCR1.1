# 04 语音模块（师弟写）— 通俗讲解笔记

> 代码：[app_audio_pcm.c](bleuart/src/app_audio_pcm.c)（麦克风采集）、[app_encoder_sbc.c](bleuart/src/app_encoder_sbc.c)（SBC 编码封装）、[sbc.c](bleuart/src/sbc.c)（开源 SBC 库）、[app_voice_ctrl.c](bleuart/src/app_voice_ctrl.c)（语音控制队列）、[blecomm.c](bleuart/src/blecomm.c)（语音帧打包）、cs/src/ble_dtss.c（语音 GATT 服务，国标附录 D 协议）
> 协议依据：GY/T 407-2024 附录 D（doc/ 里有表 D.3~D.11 截图）

## 一句话定位

遥控器长按语音键 → 麦克风连续采集 → SBC 压缩 → BLE notify 发给机顶盒 → 机顶盒解压识别。整条链路的协议（能力协商/控制/数据格式）按国标 GY/T 407-2024 附录 D 实现。

## 通俗类比：录音 → 压缩 → 打包 → 快递

```
麦克风 = 一直在录音的话筒
  ↓ ADC+DMA 双缓冲（ping-pong，像两只手交替接水，一边接一边倒）
  ↓ SBC 编码 = 把 256 字节原始 PCM 压缩成 ~68 字节（像 zip，但是为实时音频设计的）
  ↓ 打包 = 每包加 8 字节"面单"（4 字节序号 + 4 字节时间戳）
  ↓ BLE notify = 快递发出（每 8ms 一包）
  ↓ STB 按序号解压播放
```

**为什么要压缩？** 原始 PCM = 16kHz × 16bit = 256kbps，BLE 实际带宽只有 ~100kbps，传不动；SBC 压到 ~68kbps 才能过。这就是"语音必须编码"的根本原因。

## 四段式讲解

### 1. 采集段（app_audio_pcm.c）
- 硬件配置：ADC 通道 0（PB11 麦克风）→ **MICBIAS 1.6V 偏置** + **PGA 增益 42dB** + **过采样 128 倍**（2^7）→ AUDIOPLL 做 ADC 时钟（音频专用 PLL，保证采样精度）；
- **DMA 循环双缓冲**（ping-pong）：半传输/传输完成中断各计一个计数，主循环消费——**采集和编码并行，不丢数据**；
- 启动时**丢弃前 8 个半缓冲**：等 ADC 稳定；
- **周期字滤波**：发现每隔 250 个采样点出现固定的 "00 00" 干扰字，用相位锁定检测周期（容差 3 点）、锁定后逐周期剔除。

### 2. 编码段（app_encoder_sbc.c + sbc.c）
- sbc.c 是**开源 BlueZ SBC 库**（Nokia/Intel，LGPL），SBC 是 BLE 经典音频 A2DP 的标准编解码器；
- 参数：16kHz 采样 / 单声道 / 16 blocks / 8 子带 / LOUDNESS 分配 / **bitpool 30**；
- 原理一句话：把音频频带切成 8 个子带，按人耳响度曲线（LOUDNESS）分配每个子带多少 bit；
- 计算：每帧 = 16 blocks × 8 子带 × 2B = **256 字节 PCM = 8ms 音频**（16kHz 下 128 采样点）；编码后一帧 ≈ 68 字节 → **压缩比约 4:1，码率 ~68kbps**；
- PCM 累积缓冲攒够 256 字节就编一帧，编完立刻发。

### 3. 打包发送段（blecomm.c）
- 每帧加 8 字节头：**4B 序号（seq，防乱序/丢包检测）+ 4B 时间戳（每帧 +8ms，正好一帧的时长）**；
- 开始/结束各发一个状态帧（"START" / "AUDIOEND" 文本帧）；
- 热路径**不打日志**：注释写明"串口打印拖慢 taskVoice → SBC 积压 → 突发发送 → **听感语速变快**"——语音是实时流，编码按 8ms 节拍，发送慢了就积压。

### 4. 协议控制段（ble_dtss.c，国标附录 D）
- 语音服务 128-bit UUID，**三个特征**：
  - **chr0 数据通道**（READ+NOTIFY）：SBC 语音包从这里出；
  - **chr1 控制请求**（WRITE）：STB 下发命令——0x02 能力协商（codec 位图 SBC/ADPCM/OPUS/L2HC + 传输方式位图 HID/GATT）、0x01 控制（开始/停止采集）；
  - **chr2 控制响应**（READ+**INDICATE**）：能力响应/状态响应（SPEAKING/IDLE）；
- **能力协商流程**（像握手问"你会什么语言"）：STB 发自己支持的编解码位图 → 设备取交集 → 本机只支持 SBC+GATT → 回复"选 SBC"；
- **控制命令经 FreeRTOS 队列转发**（app_voice_ctrl.c 静态队列）：GATT 回调里只 post 命令，主循环消费执行——**中断/回调上下文不做重活**；
- 为什么响应用 indicate 不用 notify：indicate 需要主机在 GATT 层**确认收到**，控制类消息必须保证送达。

## 关键数字（面试脱口而出）

| 项 | 值 |
|---|---|
| 采样率 | 16kHz / 16bit / 单声道 |
| 原始码率 | 256 kbps |
| SBC 参数 | 8 子带 / 16 blocks / bitpool 30 / LOUDNESS |
| 编码后码率 | ~68 kbps（压缩比 ~4:1） |
| 帧节奏 | 每 8ms 一帧，帧头带 seq+timestamp |
| 上行通道 | BLE notify，MTU 515（244B 有效载荷/包） |
| BLE 1M 吞吐上限 | ~100kbps 实际 → 68kbps 有余量 |

## 面试自测题

1. 语音从麦克风到 STB 的完整链路？每段干什么？
2. 为什么不能直接传 PCM？SBC 是什么、参数怎么选、bitpool 影响什么？
3. ping-pong 双缓冲解决什么问题？半传输中断为什么用？
4. 帧头的 seq/timestamp 干什么用？时间戳为什么每帧 +8ms？
5. notify 和 indicate 的区别？为什么控制响应用 indicate？
6. 能力协商为什么必要？（不同厂商设备支持不同编解码/传输方式）
7. "语速变快"bug 的根因？（实时流编码节拍 vs 发送速率不匹配）
8. 周期字滤波检测什么？怎么锁定周期？
9. 语音期间为什么不能进待机态？（68kbps 需要工作态 10ms 连接间隔保带宽，所以 START 时 pm_activity_notify(PM_ACTIVITY_VOICE)）
10. 停止采集时硬件关了什么？为什么 AUDIOPLL 也要关？（省电，音频 PLL 功耗可观）
11. 16kHz 采样对语音够吗？（语音带宽约 4kHz，Nyquist 定理 8kHz 就够，16kHz 留裕量保质量）

## 与硬件岗的关联点

- 麦克风信号链：MEMS/驻极体麦 → 隔直耦合 → MICBIAS 1.6V 偏置 → PGA 42dB 放大 → ADC 过采样（原理图上 _sch_r5_mic.png 有这一块）；
- AUDIOPLL：音频专用 PLL 保证采样率精度，避免用系统时钟分频带来的频偏（频偏会导致音调变高/低）；
- 过采样 128 倍的意义：把量化噪声摊到更宽频带，等效提高信噪比；
- 低功耗联动：语音停止时 MICBIAS/PGA/AUDIOPLL 全关，麦克风偏置脚配模拟输入防上拉给麦供电（低功耗笔记里的 PB11/12/13 就是它）。
