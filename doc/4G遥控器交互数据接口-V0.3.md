## 1. 角色与原则

- RC：GATT Server
- STB：GATT Client
- RC 键值上报以 HID 为主通道，Notify 为辅助通道
- 本文所有多字节无符号整数均为大端序
- 除明确标注为 ASCII 的字段外，均为原始二进制字节流
- 连接建立后，双方先完成 MTU 交换
- 本协议中 RC-TRANS 单包最大长度固定为 128 Byte，且该长度包含 CRC
- 本协议中 RC-TRANS 单包有效载荷固定不超过 112 Byte

## 2. Service 与 Characteristic

基础服务 UUID：`19ee51a4-9ad3-7e6f-e4e7-ebc33f46a000`

| 名称 | UUID | 属性 | 方向 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| RC-READ | 19ee51a4-9ad3-7e6f-e4e7-ebc33f46a010 | Read | STB <- RC | 读取 RC 基础信息 |
| RC-CONF | 19ee51a4-9ad3-7e6f-e4e7-ebc33f46a012 | Write Request | STB -> RC | 下发 4G 传输配置 |
| RC-TRANS | 19ee51a4-9ad3-7e6f-e4e7-ebc33f46a013 | Write Request | STB -> RC | 下发待汇聚的小包数据 |
| RC-STATUS | 19ee51a4-9ad3-7e6f-e4e7-ebc33f46a014 | Read + Notify + Indicate | STB <- RC | 返回当前状态、最近结果与云侧下发参数 |
| RC-KEY-NOTIFY | 19ee51a4-9ad3-7e6f-e4e7-ebc33f46a015 | Notify | STB <- RC | RC 在 HID 上报键值的同时，通过 Notify 镜像上报键值 |

约定：

- RC-STATUS 的 Busy 状态可使用 Notify
- RC-STATUS 的配置生效、成功、失败结果应使用 Indicate
- STB 断线重连后可主动 Read RC-STATUS 获取最近状态
- RC-KEY-NOTIFY 在 HID上报的同时，同步上报键值， 优先级低于HID

## 3. 数据定义

### 3.1 RC-READ

固定长度：61 Byte

| 字段 | 类型 | 长度 | 说明 |
| :-- | :-- | :--: | :-- |
| DeviceID | ASCII | 2 | 设备编码 |
| DeviceRegionId | ASCII | 6 | 行政区划码，符合 GB/T 2260 |
| UserID | ASCII | 4 | 用户编码 |
| DeviceModel | Uint8 | 1 | 0x01=语音遥控器，0x02=4G 模块 |
| DeviceSWVersion | ASCII | 8 | 软件版本，如 `01020304` |
| DeviceStatus | Uint8 | 1 | 0x00=正常，0x01=失效，0x02=未知 |
| DeviceActiveTime | ASCII | 14 | `YYYYMMDDhhmmss`；无值填 `00000000000000` |
| DeviceInactiveTime | ASCII | 14 | `YYYYMMDDhhmmss`；无值填 `00000000000000` |
| DeviceTransmissionNetwork | Uint8 | 1 | 0x00=广电，0x01=电信，0x02=联通，0x03=移动，0x04=其他 |
| DeviceMac | Uint8[6] | 6 | MAC 地址 |
| Reserved | Uint8[4] | 4 | 预留，默认全 0 |

### 3.2 RC-CONF

固定长度：16 Byte

| 字段 | 类型 | 长度 | 说明 |
| :-- | :-- | :--: | :-- |
| ConfigTS | ASCII | 4 | 配置下发时间，格式 `HHmm` |
| TransProtocol | Uint8 | 1 | 固定 `0x01`，表示 UDP |
| MaxPacketSize | Uint16 | 2 | 单包最大长度，固定为 `128` |
| MaxRetry | Uint8 | 1 | 最大重传次数，取值范围 `0 ~ 3` |
| RetryDelayMs | Uint16 | 2 | 重试间隔，单位 ms，取值范围 `100 ~ 5000` |
| SleepDelaySec | Uint16 | 2 | RC 空闲后进入休眠的时间，单位 s，取值范围 `0 ~ 65535`；`0` 表示不自动休眠 |
| Reserved | Uint8[4] | 4 | 预留，默认全 0 |

RC 收到合法 RC-CONF 后，应更新本地配置，并通过 RC-STATUS 返回 `READY`。

### 3.3 RC-TRANS

变长结构，单次总长度不得超过 128 Byte。

| 字段 | 类型 | 长度 | 说明 |
| :-- | :-- | :--: | :-- |
| PackHeader | Uint16 | 2 | 固定 `0x55AA` |
| PackTS | ASCII | 4 | 数据包生成时间，格式 `HHmm` |
| FrameLen | Uint16 | 2 | 整帧总长度，从 `PackHeader` 到 `CRC16` 的总字节数 |
| PackIndex | Uint32 | 4 | 大包序号，范围 `0x00000000 ~ 0xFFFFFFFE`；达到 `0xFFFFFFFE` 后回卷为 `0x00000000`；刚上电时内部初始值为 `0xFFFFFFFF` |
| SubPackIndex | Uint8 | 1 | 小包序号，范围 `0x00 ~ 0xFF`；倒序下发；当序号为 `0x00` 时，当前大包收集完成，可以上报 |
| PayloadLen | Uint8 | 1 | 小包业务数据有效长度 |
| Payload | Uint8[N] | N | 业务数据，`N = PayloadLen` |
| CRC16 | Uint16 | 2 | CRC-16/CCITT-FALSE，计算范围：`PackHeader` 至 `Payload` |

约束：

- `FrameLen = 2 + 4 + 2 + 4 + 1 + 1 + PayloadLen + 2`
- `FrameLen <= 128`
- `PayloadLen <= 112`
- STB 刚上电时，发送首包前应先将 `PackIndex` 置为 `0x00000000`
- 同一大包的所有小包使用相同 `PackIndex`
- 不允许在 Payload 末尾补 0 充数；按 `PayloadLen` 解释有效数据

### 3.4 RC-STATUS

固定长度：14 Byte

| 字段 | 类型 | 长度 | 说明 |
| :-- | :-- | :--: | :-- |
| State | Uint8 | 1 | 0x00=IDLE，0x01=READY，0x02=BUSY，0x03=DONE，0x04=ERROR |
| Result | Uint8 | 1 | 0x00=NONE，0x01=OK，0x02=CRC_ERROR，0x03=LEN_ERROR，0x04=PARAM_ERROR，0x05=DUPLICATE，0x06=BUSY_REJECT，0x07=NET_ERROR |
| RetryCount | Uint8 | 1 | 最近一个包的实际重传次数 |
| Reserved1 | Uint8 | 1 | 预留，默认 0 |
| PackIndex | Uint32 | 4 | 最近完成处理的包序号；无有效值时为 `0xFFFFFFFF` |
| CloudUploadPolicy | Uint8[6] | 6 | 云端通过 CAT1 下发的上传参数；前 4 Byte 为上传间隔 `UploadIntervalSec`，后 2 Byte 为每次上传条数 `UploadItemCount` |

说明：

- `State=READY` 表示配置已生效，可接收 RC-TRANS
- `State=BUSY` 表示 RC 正在执行 4G 上传
- `State=DONE` 表示最近一个包处理成功
- `State=ERROR` 表示最近一个包处理失败，失败原因见 `Result`

### 3.5 RC-KEY-NOTIFY

固定长度：4 Byte

| 字段 | 类型 | 长度 | 说明 |
| :-- | :-- | :--: | :-- |
| KeyType | Uint8 | 1 | 0x01=Keyboard，0x02=Consumer，0x03=Voice |
| KeyAction | Uint8 | 1 | 0x00=Release，0x01=Press |
| KeyValue | Uint16 | 2 | 键值 |

说明：

- RC 通过 HID 上报键值的同时，应通过 RC-KEY-NOTIFY 上报同一键值事件
- RC-KEY-NOTIFY 仅用于业务同步，不替代 HID 输入通道

## 4. 交互流程

### 4.1 初始化流程

1. STB 扫描并连接 RC。
2. 连接成功后，双方完成 MTU 交换。
3. STB 发现基础服务与 5 个特征值。
4. STB 使能 RC-STATUS 与 RC-KEY-NOTIFY 的 CCCD。
5. STB 读取 RC-READ，校验 DeviceID、DeviceMac、DeviceStatus。
6. STB 写入 RC-CONF。
7. RC 配置生效后，通过 RC-STATUS 返回：`State=READY, Result=OK`。
8. STB 收到 READY 后，方可发送 RC-TRANS。

RC-CONF 下发时机：

- 推荐在 RC 每次唤醒后的首次连接中下发
- 若 RC 发生重连、重启或配置参数变更，STB 应重新下发
- 在未收到 `READY` 前，STB 不得发送 RC-TRANS

### 4.2 单包上传流程

1. STB 将一个大包拆分为多个 RC-TRANS 小包；同一大包的小包使用相同 `PackIndex`。
2. STB 为每个小包分配 `SubPackIndex`；允许倒序发送。
3. STB 以 Write Request 逐个写入 RC-TRANS。
4. RC 收到每个小包后先校验包头、长度、CRC，并按 `PackIndex + SubPackIndex` 缓存。
5. 校验失败时，RC 通过 RC-STATUS 返回 `State=ERROR`，并给出对应 `Result`。
6. 当 RC 收到 `SubPackIndex = 0x00` 的小包时，判定当前大包收集完成，开始 CAT1 上传，并返回 `State=BUSY, Result=NONE`。
7. RC 完成 CAT1 上传后：
   - 成功：返回 `State=DONE, Result=OK, PackIndex=当前大包序号`
   - 失败：返回 `State=ERROR, Result=NET_ERROR, PackIndex=当前大包序号`
8. STB 仅在收到 `DONE/OK` 后，才发送下一个大包。
9. RC 在 `BUSY` 状态下不得进入休眠。

### 4.3 重传流程

1. STB 在以下任一条件成立时执行重传：
   - RC 返回 `ERROR`
   - RC-TRANS 的 Write Request 超时或失败
   - RC 在约定超时时间内未返回最终结果
2. 重传前，STB 更新 `PackTS`，`PackIndex` 与 `SubPackIndex` 保持不变。
3. 单个小包累计重传次数不得超过 `MaxRetry`。
4. 超过 `MaxRetry` 后，STB 将当前大包记为失败，不再继续发送该大包。
5. 当 `PackIndex` 达到 `0xFFFFFFFE` 后，下一新大包的 `PackIndex` 从 `0x00000000` 重新开始。

### 4.4 重复包与乱序处理

1. RC 同一时刻仅允许一个正在汇聚或上传的大包。
2. 当 RC 处于 `BUSY` 时，收到新包应返回 `State=ERROR, Result=BUSY_REJECT`。
3. 对于同一大包，RC 依据 `PackIndex + SubPackIndex` 识别小包是否重复。
4. 若收到重复的小包，RC 应返回 `State=ERROR, Result=DUPLICATE`。
5. 若 RC 最近成功处理的大包序号为 `0xFFFFFFFE`，则应允许下一新大包的 `PackIndex = 0x00000000`。
6. 除上述回卷场景外，若收到的 `PackIndex` 小于最近成功处理的大包序号，RC 应返回 `State=ERROR, Result=DUPLICATE`。

### 4.5 断线恢复流程

1. 蓝牙断开后，STB 重新扫描并连接 RC。
2. 重连后重复执行初始化流程中的步骤 2 至步骤 4。
3. STB 读取 RC-STATUS。
4. 若 `State=DONE` 且 `PackIndex` 为最近已完成包，则从下一包继续。
5. 若 `State=BUSY`，STB 等待 RC 返回最终结果；超时后按重传流程处理。
6. 若 `State=ERROR`，STB 根据 `Result` 决定是否重传最近一包。

### 4.6 休眠进入规则

1. RC 仅在以下条件同时满足时允许进入休眠：
   - 当前状态为 `IDLE` 或 `READY`
   - 不存在待处理 RC-TRANS
   - 距离最近一次有效交互已达到 `SleepDelaySec`
2. RC 进入休眠前，不主动上报额外状态。
3. RC 从休眠恢复后，应重新进入可连接状态。
4. STB 发起新一轮业务前，应先确保 RC 已连接并完成初始化流程。

### 4.7 按键上报流程

1. RC 检测到键值事件后，先按原有 HID 流程上报。
2. 同一键值事件，RC 同时通过 RC-KEY-NOTIFY 发送一帧 Notify 数据。
3. STB 接收到 RC-KEY-NOTIFY 后，用于业务同步处理。
4. 若 HID 与 RC-KEY-NOTIFY 同时存在，以 HID 作为输入主通道。

## 5. 实施约束

- RC-CONF 与 RC-TRANS 仅允许在加密连接下访问
- RC-STATUS 不做周期性空闲上报；仅在状态变化时上报，或由 STB 主动读取
- RC-KEY-NOTIFY 仅用于镜像上报键值，不替代 HID
- STB 未收到 RC-STATUS 的 READY 前，不得发送 RC-TRANS
- 同一时刻仅允许一个未完成业务包在链路中传输
- RC 处于 `BUSY` 时不得进入休眠
- 若 RC 允许自动休眠，STB 不应假设 RC 始终在线
