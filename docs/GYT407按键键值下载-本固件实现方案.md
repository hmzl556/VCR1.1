# GY/T 407-2024 按键键值下载 —— 本固件实现方案

> **文档定位**：本文是 [GYT407按键键值下载功能说明.md](./GYT407按键键值下载功能说明.md) 的落地实现篇。
> 前者讲“规范要求什么”，本文讲“在 `20IWDG` 这个工程里具体怎么改、加哪些文件、占多少 Flash/RAM、哪里会冲突”。
>
> **范围约定（已确定）**
> - 只做**键值下载**，不做规范附录 E.2 的固件更新（固件升级走 CAT1 UDP OTA）；
> - 双控形态：**机顶盒 蓝牙+红外，电视机只走红外**（无 `bletv`）；
> - 键值套数：三套（`blestb` / `irstb` / `irtv`）。

## 二、总体架构

```
APP（通用遥控）
   │  BLE write_cmd / notify
   ▼
[新增] ble_upg_svc.c ──── GATT 服务（表 A.5）──── 特征 1d2b31
   │  投递原始帧到任务（不在回调里做 Flash/IR）
   ▼
[新增] upg_proto.c ───── 20 个接口状态机（0xF9/0xFA，操作码 0x11~0x22）
   ├─► upg_auth.c ───── 双向 MD5 认证
   ├─► upg_meta.c ───── rel0 硬件信息 / usr1 版本信息
   └─► 按数据类型分派
        ├─ irtv / irstb ─► ir_key_file.c ─► ir_pw_bp.c ─► ir_raw_t
        └─ blestb ───────► ble_key_file.c ─► 键值映射表

[新增] key_store.c ───── Flash 覆盖层（版本 + CRC + 双份）
        ▲                │
        │                ▼
   key_table.c ───── 三层查表：学习值 > 下载值 > 出厂默认
        │
        ├─► ir_key_map.c   （红外发送）
        └─► ble_hid_kbd.c  （BLE HID 发送）
```

**设计原则**

1. **回调只收帧，不做业务**：GATT 回调里只 memcpy 到缓冲区并置标志，Flash 写、MD5、解析全部在任务上下文完成（现状 `ble_rc_svc.c` 已是这个模式）。
2. **下载值不存原始波形**：只存 `协议表索引 + 码值`，运行时再合成波形，省 Flash。
3. **复用现有发送驱动**：PW/BP 编码结果填充成 `ir_raw_t`，交给 `ir_rc6_send_wave()`，发送层零改动。

## 三、新增 GATT 服务（如何写）

### 3.1 UUID 与字节序

规范值：

- 服务：`10111213-1415-1617-1819-1a1b1c1d1931`
- 特征：`10111213-1415-1617-1819-1a1b1c1d2b31`

**注意：本 SDK 的 `uuid128` 数组是反序存放的**（见 `ble_rc_svc.c:542` 的 19ee51a4… 写成 `{0x00,0xa0,0x46,…}`）。所以应写成：

```c
/* 10111213-1415-1617-1819-1a1b1c1d1931 反序 */
static const uint8_t UPG_SVC_UUID[16] = {
    0x31, 0x19, 0x1d, 0x1c, 0x1b, 0x1a, 0x19, 0x18,
    0x17, 0x16, 0x15, 0x14, 0x13, 0x12, 0x11, 0x10
};
/* 10111213-1415-1617-1819-1a1b1c1d2b31 反序 */
static const uint8_t UPG_CHR_UUID[16] = {
    0x31, 0x2b, 0x1d, 0x1c, 0x1b, 0x1a, 0x19, 0x18,
    0x17, 0x16, 0x15, 0x14, 0x13, 0x12, 0x11, 0x10
};
```

### 3.2 服务注册骨架

```c
/* bleuart/cat1/cat1/UPG/ble_upg_svc.c */
#include "ble_upg_svc.h"
#include "gatt.h"
#include "gap.h"
#include "co_printf.h"

static gatt_svc_t  s_upg_svc;
static gatt_chr_t  s_upg_chr;
static peer_t      s_upg_peer;
static uint16_t    s_upg_mtu = 23u;      /* 协商后更新，最小 139 */
static uint8_t     s_upg_rx[UPG_RX_MAX]; /* write_cmd 落地缓冲 */
static volatile uint8_t s_upg_rx_pending;

static void upg_svc_cbk(gatt_event_t ev, void *ctx, void *param)
{
    if (ev == GATTS_EV_SERVICE_START) {
        gatt_svc_start_t *in = param;
        co_printf("[UPG ] svc start=%X\r\n", in->result);
    }
}

static void upg_chr_cbk(gatt_event_t ev, void *ctx, void *param)
{
    if (ev == GATTS_EV_CHR_VALUE_WRITE_REQ || ev == GATTS_EV_CHR_VALUE_WRITE) {
        gatt_chr_val_write_req_t *in = param;
        s_upg_peer = in->peer;
        if (in->val_len == 0u || in->val_len > UPG_RX_MAX) {
            if (ev == GATTS_EV_CHR_VALUE_WRITE_REQ)
                gatts_chr_val_write_rsp(in->peer, in->chr,
                                        GATT_RES_INVALID_ATTRIBUTE_VALUE_LENGTH);
            return;
        }
        memcpy(s_upg_rx, in->val, in->val_len);
        s_upg_rx_len = in->val_len;
        s_upg_rx_pending = 1u;      /* 由任务消费，不在回调里解析 */
        if (ev == GATTS_EV_CHR_VALUE_WRITE_REQ)
            gatts_chr_val_write_rsp(in->peer, in->chr, GATT_OK);
    } else if (ev == GATTS_EV_CHR_VALUE_READ_REQ) {
        gatt_chr_val_read_req_t *in = param;
        gatts_chr_val_read_rsp(in->peer, in->chr, GATT_OK,
                               s_upg_last_tx, s_upg_last_tx_len);
    } else if (ev == GATTS_EV_CHR_VALUE_SEND_START) {
        gatt_chr_val_send_start_t *in = param;
        if (in->type == GATT_SEND_VAL_NOTIFICATION) s_upg_cccd_on = 1u;
        s_upg_peer = in->peer;
    }
}

int ble_upg_svc_init(void)
{
    uuid_t svc_uuid = { UUID_LEN_128, { .uuid128 = {
        UPG_SVC_UUID_BYTES } } };
    uuid_t chr_uuid = { UUID_LEN_128, { .uuid128 = {
        UPG_CHR_UUID_BYTES } } };

    s_upg_svc = gatts_svc_create(&svc_uuid, upg_svc_cbk, NULL);
    s_upg_chr = gatts_chr_add(s_upg_svc, &chr_uuid,
                              GATT_CHR_PROP_READ |
                              GATT_CHR_PROP_WRITE |
                              GATT_CHR_PROP_WRITE_WITHOUT_RSP |
                              GATT_CHR_PROP_NOTIFY,
                              ATT_PERM_READ | ATT_PERM_WRITE,
                              upg_chr_cbk, NULL);
    gatts_dsc_ccc_add(s_upg_chr, GATT_CHR_PROP_NOTIFY,
                      ATT_PERM_READ | ATT_PERM_WRITE);
    gatts_svc_start(s_upg_svc);
    return 0;
}

/* 统一 notify 出口：命令字 0xFA，长度受 MTU 限制 */
int ble_upg_notify(const uint8_t *buf, uint16_t len)
{
    if (!s_upg_peer || !s_upg_cccd_on) return -1;
    return gatts_chr_val_notif(s_upg_peer, s_upg_chr, (uint8_t *)buf, len) == GATT_OK ? 0 : -1;
}
```

**要点**

| 项 | 说明 |
|---|---|
| `write_cmd`（无响应写） | 用 `GATT_CHR_PROP_WRITE_WITHOUT_RSP`，对应 `GATTS_EV_CHR_VALUE_WRITE`；否则每一包都要等 ATT 响应，吞吐无法满足下载 |
| 注册顺序 | **必须在 `ble_gap_init()` 之前**（`main.c:118` 注释已说明 peer_recover 依赖服务已创建） |
| 初始化调用点 | `main.c` 的 `ble_stack_init_only()` 内，`ble_rc_svc_init()` 之后加一行 `ble_upg_svc_init();` |

### 3.3 MTU 处理（现状有缺口）

现状 `ble_gap.c:486` 请求 515，但 `ble_gap_mtu_exchange()`（`ble_gap.c:505`）里接收到的 MTU **被注释掉没有保存**：

```c
//ble_att_mtu = arg->mtu;   /* 现状：未保存 */
```

**必须补上**，否则无法按实际 MTU 计算分包长度：

```c
static uint16_t s_att_mtu = 23u;
void ble_gap_mtu_exchange(gap_event_t ev, void *ctx, att_mtu_ntf_t *arg)
{
    s_att_mtu = arg->mtu;
    ble_upg_set_mtu(arg->mtu);      /* 新增：通知下载模块 */
}
uint16_t ble_gap_get_mtu(void) { return s_att_mtu; }
```

分包规则：`len = min(MTU - 3, 128)`，且只能取 **16 / 32 / 64 / 128**（规范 E.1.1.3.1）。若协商后 MTU=139，则 `139-3=136` → 取 **128**，满足要求；若对端只给 23，则 `23-3=20` → 取 **16**，仍合规但很慢，需在状态上报里体现。

## 四、协议状态机

### 4.1 状态定义

```c
typedef enum {
    UPG_IDLE = 0,
    UPG_AUTH_WAIT_HOST,     /* 等主机认证响应 */
    UPG_AUTH_WAIT_RC,       /* 等主机发起遥控器认证 */
    UPG_AUTH_OK,
    UPG_READ_ACTIVE,        /* 启动读之后，上行传输中 */
    UPG_WRITE_ACTIVE,       /* 启动写之后，下行接收中 */
    UPG_WAIT_CRC,           /* 数据传完，等终止读写请求 */
    UPG_ERROR
} upg_state_t;
```

### 4.2 分派表

| 命令字 | 操作码 | 处理 | 状态迁移 |
|---|---|---|---|
| 0xF9 | 0x11 | 启动读请求 | → READ_ACTIVE |
| 0xF9 | 0x12 | 启动写请求 | → WRITE_ACTIVE |
| 0xF9 | 0x13 | 终止读写（带 CRC1） | 比对 → 成功写 Flash 提交 |
| 0xF9 | 0x14 | 下行数据 | 累积写缓冲 |
| 0xF9 | 0x15/0x16 | 获取/设置升级标志 | 不变 |
| 0xF9 | 0x20 | 升级主机认证响应 | → AUTH_WAIT_RC |
| 0xF9 | 0x21 | 遥控器认证请求 | → AUTH_OK |
| 0xF9 | 0x22 | 写指令配置 | 不变 |

### 4.3 缓冲与并发

- **单包缓冲** `s_upg_rx[140]`（放 `UPG_RX_MAX`），收发复用；
- 大文件**不整包缓存**：解析器边收边解（流式），只有键值条目与协议表驻留；
- 协议表解析结果放**共享 scratch 缓冲**（见第九节），不常驻。

### 4.4 任务侧驱动

在 `app_rtos` 的既有任务里增加一处轮询（与 `ir_tx_process()` 同级）：

```c
void upg_task_poll(void)
{
    if (s_upg_rx_pending) {
        s_upg_rx_pending = 0u;
        upg_proto_on_frame(s_upg_rx, s_upg_rx_len);
    }
    upg_flash_commit_poll();   /* 分片写 Flash + 喂狗 */
}
```

## 五、认证

### 5.1 实现要点

```c
/* hash = MD5( key[16] || rand[16] || idcode[32] ) */
void upg_auth_hash(const uint8_t *key, const uint8_t *rand,
                   const uint8_t *idcode, uint8_t out[16])
{
    MD5_CTX ctx;
    MD5Init(&ctx);
    MD5Update(&ctx, key, 16);
    MD5Update(&ctx, rand, 16);
    MD5Update(&ctx, idcode, 32);
    MD5Final(&ctx, out);
}
```

- 算法照附录 J 的参考代码实现，**拼接顺序必须是 key → rand → idcode**；
- 比对时**不区分大小写**（规范原文），实现上按字节比较即可，但若对方以十六进制字符串传哈希，需先统一大小写；
- 计算量：3 次 update + 1 次 final，M0 上约 0.3~0.5 ms，**不阻塞低功耗策略**（认证期间本来就不能休眠）。

### 5.2 密钥存放

| 数据 | 建议位置 | 说明 |
|---|---|---|
| `idcode`（32 B） | Flash 独立扇区 | 产测写入，随设备唯一 |
| `key`（16 B × N） | 同上 | 支持 `key_index` 多组 |

不建议放 ROM：固件一旦被读出，密钥就公开了；放 Flash 至少可以产测单独写入、可换密钥。

### 6.1 数据结构


容量估算：

| 表 | 条目数 | 单条 | 小计 |

| 红外三套 | 3 × 30（表 B.1 序号上限） | 4 B | 360 B |
| 蓝牙一套 | 30 | 4 B | 120 B |
| **ROM 默认表合计** | | | **≈ 480 B（RO）** |

### 6.2 三层结构与优先级

```
第 1 层  学习值      Flash 波形区 A/B（现状，仅 4 个键）
第 2 层  下载值      Flash 覆盖层（新增）
第 3 层  出厂默认    ROM（新增的三套表）
```

优先级依据规范 7.4“键值以最后更新的为准”，因此**不能简单固定为“学习优先”**，两层都要带序号：

```c
typedef struct {
    uint16_t seq;     /* 单调递增，写入时取 max(现有)+1 */
    uint32_t stamp;   /* 可选：写入时刻 */
} layer_ver_t;
```

查表逻辑：

```c
bool key_lookup_ir(uint8_t key, key_tgt_t tgt, ir_ent_t *out);
bool key_lookup_ble(uint8_t key, ble_ent_t *out);
```

### 6.3 接入点

| 位置 | 改法 |
|---|---|
| `ir_key_map.c:86` `ir_send_key()` | 现在是“有学习波形就短路”。改成：
① 查学习层（带序号）→ ② 查下载层（带序号）→ ③ 比序号取较新 → ④ 都没有则用 ROM 默认 |

| `task_keyscan.c:681` 按键路由 | 由“BLE 连没连”改为“按键归属 + 连接状态”二维判定（见功能说明双控路由表） |

## 七、文件解析与发码

### 7.1 红外 ETV 解析（流式）

```c
typedef struct {
    uint8_t  enc;            /* 1=PW 2=BP */
    uint8_t  freq;           /* 1..6 → 36/37/38/39/40/56 kHz */
    uint8_t  duty;           /* 1..4 → 1/2,1/3,1/4,1/5 */
    uint8_t  scale;
    uint8_t  repeat_mode;
    uint8_t  table_num;
    /* 协议表 */
    struct {
        uint16_t unit;       /* BP 专用 */
        uint8_t  has_start, has_toggle;
        uint8_t  data_bit_num, header2_pos, col_num;
        uint16_t b0[2], b1[2], b2[2], b3[2];
        uint16_t header[2], header2[2];
        struct { uint8_t bit_num, ref_col; uint8_t has_hdr; uint16_t burst[2]; } col[UPG_COL_MAX];
    } t[UPG_TBL_MAX];
} etv_ctx_t;
```

限制：`UPG_TBL_MAX = 4`、`UPG_COL_MAX = 8`，超出即判文件不合规（正常遥控器远小于此）。整个 `etv_ctx_t` 约 350 B，**放共享 scratch，不常驻**。

### 7.2 PW/BP → `ir_raw_t`

```c
/* 把码值按协议表编码成电平宽度数组，直接复用现有发送驱动 */
bool ir_enc_build_wave(const etv_ctx_t *c, uint8_t tbl,
                       const uint8_t key_value[8], ir_raw_t *out);
```

- 输出 `out->period_ticks = 64000000UL / (freq_khz * 1000)`；
- `out->kind = IR_RAW_KIND`，`out->widths[]` 填高低电平时长；
- 交给 `ir_rc6_send_wave(out, repeat)` —— **该函数内部会拷贝一份到堆，调用后 out 可复用**（`ir_rc6.c:147` 已确认）。

**段数上限**：`IR_RAW_MAX = 255`。32 位码值约 67 段，8 字节 × 8 位 = 128 位约 259 段，**可能溢出**，需在解析时按 `bit_num` 预估并拒绝超限条目。

### 7.3 蓝牙 E.25 解析

只需支持 `device_type ≥ 0x80000000`（机顶盒）的条目；遇到电视机条目直接跳过并打印日志。解析产出 `fc2hid`（key_fcode → usage/page/modifier）与 `fc2no`（key_fcode2 → 表 B.1 序号）两张映射，转成 `ble_ent_t` 写入覆盖层。

## 九、Flash 分区方案

### 9.1 方案 A：不改 Bootloader（推荐先做）

只使用现有 60 KB 未分配区，**不动任何既有地址**：

| 区域 | 地址 | 大小 | 用途 |
|---|---|---|---|
| 键值覆盖层 | 0x01071000 | 4 KB | 记录式覆盖层，双份 + CRC |
| 认证密钥 | 0x01072000 | 4 KB | `idcode` + 多组 `key`，产测写入 |
| 预留 | 0x01073000 | 52 KB | 后续扩展 |

### 9.2 覆盖层记录格式

```c
#define KEYSTORE_MAGIC   0x4B53544Fu   /* 'KSTO' */
#define KEYSTORE_VER     1u

typedef struct {
    uint32_t magic;
    uint16_t version;
    uint16_t seq;             /* 本次提交序号，取大者生效 */
    uint8_t  tgt;             /* key_tgt_t */
    uint8_t  key;             /* 表 B.1 功能序号 */
    uint8_t  kind;            /* 同 ir_ent_t.kind；蓝牙固定 0xA5 */
    uint8_t  user;
    uint8_t  tbl;
    uint8_t  cmd;
    uint8_t  reserved[2];
    uint16_t crc;             /* 覆盖本条前面所有字节 */
} keystore_rec_t;   /* 20 B */
```

- 4 KB 扇区可放 **200 条**记录，三套 × 30 键 = 90 条，写满一半；
- 每套键值另有一条**版本记录**（`tgt=0xFF`），承载规范 `usr1` 的版本字段；
- 提交顺序：先写数据记录 → 读回校验 → 最后写版本记录，**版本记录写成功才算生效**（与现有 `ir_wave_store` 的“最后写 magic”思路一致）；
- 扇区写满时整扇区擦除后重写（需先在 RAM 里保留当前有效集，或用另一份备份扇区，二选一）。

### 9.3 方案 B：扩 APP1 代码区（只有方案 A 的代码装不下时才用）

| 区域 | 地址 | 大小 |
|---|---|---|
| Bootloader | 0x01000000 | 16 KB |
| APP1 | 0x01004000 | **220 KB** |
| APP2 | 0x0103B000 | **220 KB** |
| OTA 配置 | 0x01072000 | 4 KB |
| BLE 绑定 | 0x01073000 | 4 KB |
| 云策略 | 0x01074000 | 4 KB |
| 红外波形 A | 0x01075000 | 12 KB |
| 红外波形 B | 0x01078000 | 12 KB |
| 键值覆盖层 | 0x0107B000 | 4 KB |
| 认证密钥 | 0x0107C000 | 4 KB |
| 预留 | 0x0107D000 | 12 KB |

> **代价**：`flash_layout.h`、`ble_dtss.sct`、`tools/build.ps1`、**以及本工程之外的 Bootloader** 全部要改。
> **风险**：已出货设备的 Bootloader 仍指向旧地址，必须先升级 Bootloader 才能用新 APP1，不能只靠 OTA。

## 十、RAM 预算

### 10.1 需求明细

| 项目 | 字节 | 说明 |
|---|---|---|
| GATT 收包缓冲 `s_upg_rx` | 140 | MTU 139 上限 |
| notify 组包缓冲 | 140 | 可与收包分时复用，保守按独立计 |
| MD5 上下文 + 摘要 | 96 | 64 B block + 16 B digest + 16 B 状态 |
| 认证临时（rand/idcode/key） | 64 | idcode 从 Flash 读，用时读 |
| 协议表 `etv_ctx_t` | 350 | 放 scratch |
| 合成波形 `ir_raw_t` | 522 | 放 scratch |
| 版本信息缓存 | 80 | 9 个字段 |
| 状态机 + 标志 + 序号 | 40 | |
| **小计（不含 scratch）** | **560** | |
| **scratch 峰值** | **522** | 与 560 不同时占用 |

### 10.2 与现状对比

```
需求：约 560 B（+ scratch 522 B，可与现有缓冲复用）
可用：84 B（RW_IRAM0 60 B + RW_IRAM1 24 B）
缺口：约 480 B
```

### 10.3 腾挪方案（按优先级）

1. **确认芯片 RAM 上限**（最重要）
   scatter 现在把栈顶定在 0x2000C000（48 KB），但 `uvprojx` 里写的是通用模板 `IRAM(0x20000000,0x20000)`（128 KB）。**先查芯片手册确认实际 RAM**：若大于 48 KB，直接扩 `RW_IRAM1` 的 Max，零代码改动。

2. **共享 AES 工作缓冲**（可回收 608 B）
   `aes_transport.c:16` 的 `s_aes_work[CAT1_UDP_MAX_UDP_PDU]` = **608 B**。它与键值下载**天然互斥**（一个走 CAT1，一个走 BLE，且都需要“Flash/发送独占”锁），可抽成 `upg_scratch` 统一分配。

3. **共享 OTA 写缓冲**（可回收 512 B）
   `udp_bootload.c:23` 的 `s_flash_wr_buf[OTA_CHUNK_SIZE]` = 512 B，仅 OTA 写片时使用。

4. **收/发共用一个 140 B 缓冲**
   协议是严格请求—响应式，收包处理完才发包，可复用到 140 B（省 140 B）。

5. 若以上仍不足：压缩 CAT1 AT 行缓冲（`CAT1_AT_LINE_MAX` = 1264 B，`cat1_udp_config.h:68`），或语音 PCM 缓冲。

**结论**：走 2+3+4 即可满足 560 B 需求，**不需要动现有业务缓冲**。

## 十二、冲突清单（重点）

| # | 冲突 | 实测数据 | 影响 | 建议 |
|---|---|---|---|---|
| **C1** | **Flash 代码区不足** | 余 14,080 B，本功能约需 16 KB | 装不下，超出约 2~4 KB | ①先裁调试打印（`co_printf` 目前 600 B 代码 + 大量串，可回收 2~3 KB）；②或分两期，一期只做 `irtv`/`irstb`；③仍不够再走方案 B 改分区（但需改 Bootloader） |
| **C2** | **RAM 只剩 84 B** | 需求约 560 B | 无法直接实现 | 共享 AES 608 B + OTA 512 B 缓冲；收/发共用 140 B；并**优先确认芯片真实 RAM 上限** |
| **C3** | **MTU 未保存** | `ble_gap.c:508` 被注释 | 分包长度无法计算，可能超 MTU 被截断 | 补保存 + `ble_gap_get_mtu()`，分包按 `min(MTU-3,128)` 取 16/32/64/128 |
| **C4** | **HID 消费类仅 3 个 usage** | 报告描述符为 3 位位图（`ble_hid_kbd.c:67`） | 下载的 `page=0x0C` 键值若不在 0xE2/0xE9/0xEA 内，**发不出去** | 改报告描述符为 16 位数组（会影响机顶盒解析），**必须与机顶盒方确认后再动** |
| **C5** | **载波占空比只支持 1/3** | `ir_rc6.c:153` 固定 `(period+1)/3` | 规范允许 1/2、1/3、1/4、1/5，其他三种编出来的波形占空比不对，可能收不到 | 给 `ir_rc6_send_wave()` 增加 duty 参数（或从 `ir_raw_t` 扩展字段带入） |
| **C6** | **重复码策略不足** | `ir_rc6_send_wave()` 只有“整帧重发”和“NEC 重复帧”两种 | 规范 `repeat_mode` 有 AAAA / ABBB / ABAB 三种，ABBB 与 ABAB 无法表达 | 扩展发送层：按 `key_id=1002` 的重复码条目单独发 |
| **C7** | **学习层与下载层优先级冲突** | `ir_send_key()` 现在“有学习值就短路” | 下载后若该键有旧学习值，下载值不生效，违反“以最后更新为准” | 两层都带 `seq`，比大小取新 |
| **C8** | **表 B.1 序号 ↔ 物理键无映射** | 现有 KEY1..18，表 B.1 是 1..30 | 文件里的 `key_no` 无法落地 | 新增映射表；注意“直播业务”键新增后编号会变 |
| **C9** | **单 BLE 链路** | `ble_gap.c:108` 只有一个 `g_peer` | `bletv` 不可用（已确定不做） | 解析时拒绝电视蓝牙条目 |

| **C11** | **构建脚本硬编码地址** | `tools/build.ps1:12` 检查 `RW_IRAM1 0x2000BBE0`、`MCU_STACK 0x2000BC00`、`ER_IROM1 0x01036000` | 改分区/扩 RAM 后构建立刻报错 | 与布局改动同一次提交一起改 |
| **C12** | **CRC16 参数可能不一致** | 现有 `ota_crc.c` 的 CRC 实现未按附录 J 核对 | 终止读写请求的 CRC 比对会一直失败 | 单独实现 `upg_crc`，用附录 J 的用例验证后再决定是否替换 |
| **C13** | **认证密钥未定** | 无 | 整个流程走不通 | 冻结为开发前置条件，产测工具需支持写入 |

## 十五、结论

1. **功能可实现，架构清晰**：GATT 服务 + 协议状态机 + 三层键值表 + 复用现有发送驱动，12 个新文件约 16 KB 代码。
2. **两个硬约束必须先解决**：代码区余 14,080 B（缺 2~4 KB）、RAM 余 84 B（缺约 480 B）。
3. **RAM 有干净的解法**：共享 AES 608 B / OTA 512 B 缓冲，不动业务内存。
4. **代码区解法有代价**：要么裁代码，要么改分区（改分区必须同步改 Bootloader，已出货设备风险高）。
5. **规范层面还有三处需要适配**：载波占空比（仅 1/3）、重复码模式（缺 ABBB/ABAB）、HID 消费类 usage（仅 3 个）。
6. **认证密钥和附录 I 样本是外部前置条件**，没有就无法进入 P1。
