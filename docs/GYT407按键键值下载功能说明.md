# GY/T 407-2024 按键键值下载功能说明

> **本文只覆盖「APP 下载按键键值」这一项功能。**
> 遥控器固件升级已通过 CAT1 的 UDP OTA 实现，**不采用规范附录 E.2 的固件更新流程**，故本文不包含 E.2 及 `fw01` 数据类型。
>
> **双控形态已确定：机顶盒支持蓝牙 + 红外，电视机只支持红外（无蓝牙）。**
> 对应规范 5.1.1.3.3 允许的「红外 + 蓝牙」组合，因此键值下载只涉及三套：机顶盒蓝牙、机顶盒红外、电视机红外，`bletv`（电视机蓝牙）不做。
>
> 依据：GY/T 407-2024《机顶盒通用遥控技术要求和测量方法》

## 二、功能定位

客户提出的方案是：遥控器内保存按设备和通道划分的键值数组，APP 下载后修改对应按键的值，恢复出厂后回到默认值。

**按已确定的双控形态，实际只需三套：**

| 套别 | 规范数据类型 | 说明 |
|---|---|---|
| 机顶盒蓝牙 | `blestb` | 连接时按键走 HID |
| 机顶盒红外 | `irstb` | 未连接或蓝牙不可用时的红外兜底 |
| 电视机红外 | `irtv` | 电视机唯一控制通道 |
| ~~电视机蓝牙~~ | ~~`bletv`~~ | **不做**（电视机无蓝牙） |

这与规范的关系：

- 规范用**数据类型标识**区分各套键值，本方案使用其中三套；
- 规范用**键值文件**承载内容，不是简单的“一个字节的键值”；
- 规范对“恢复出厂回默认”的支撑方式是：出厂默认值固化在固件里，下载值单独存放，恢复出厂时丢弃下载值即可。

**结论：客户方案与规范一致，可以直接采用，落地形态是“固件内出厂默认表 + Flash 下载覆盖层”。**

### 双控路由（已确定形态）

| 按键归属 | 机顶盒蓝牙已连接 | 机顶盒蓝牙未连接 |
|---|---|---|
| 机顶盒键 | 发 BLE（HID） | 发红外（`irstb`） |
| 电视机键 | 发红外（`irtv`） | 发红外（`irtv`） |
| 当前活跃设备 / 焦点设备键 | 按状态判定后分发 | 按状态判定后分发 |

**电视机始终只走红外，与蓝牙连接状态无关。**

## 三、服务与接口

### 3.1 服务定义（表 A.5）

| 项目 | 值 |
|---|---|
| 服务 UUID | `10111213-1415-1617-1819-1a1b1c1d1931` |
| 升级数据特征 UUID | `10111213-1415-1617-1819-1a1b1c1d2b31` |
| 特征属性 | read / write_cmd / notify |
| **MTU 最小值** | **139 字节**（E.1.1.2 强制要求） |

### 3.2 命令字方向

| 命令字 | 方向 |
|---|---|
| `0xF9` | 升级主机（APP）→ 遥控器 |
| `0xFA` | 遥控器 → 升级主机 |

### 3.3 接口清单（共 20 个，操作码映射）

| 操作码 | 接口 | 交互方式 |
|---|---|---|
| 0x11 | 启动读请求 | write_cmd |
| 0x11 | 启动读响应 | notify |
| 0x12 | 启动写请求 | write_cmd |
| 0x12 | 启动写响应 | notify |
| 0x13 | 终止读写请求（**带 CRC16**） | write_cmd |
| 0x13 | 终止读写响应（**带 CRC16**） | notify |
| 0x14 | 上行数据传输 | notify |
| 0x14 | 下行数据传输 | write_cmd |
| 0x18 | 下行数据传输响应 | notify |
| 0x14 | 终止数据传输（长度 0） | notify |
| 0x15 | 获取升级标志请求 / 响应 | write_cmd / notify |
| 0x16 | 设置升级标志请求 / 响应 | write_cmd / notify |
| 0x20 | 升级主机认证请求 / 响应 | notify / write_cmd（**方向相反**） |
| 0x21 | 遥控器认证请求 / 响应 | write_cmd / notify |
| 0x22 | 写指令配置请求 / 响应 | write_cmd / notify |

> 注：`0x15/0x16` 升级标志在 E.3.4 下载流程中仍被使用（下载开始前置有效、结束后置无效），**必须实现**，与固件升级无关。

### 3.4 关键帧格式（摘要）

| 接口 | 字段 |
|---|---|
| 启动读请求 | 0xF9 / 0x11 / 包长(16·32·64·128) / 数据类型(8 字节 ASCII，不足补 0) |
| 启动读响应 | 0xFA / 0x11 / 结果 / 数据地址(4，高字节在前) / 数据长度(4) |
| 启动写请求 | 0xF9 / 0x12 / 包长 / 数据类型(8 字节) / 保留(4) / 数据长度(4) |
| 启动写响应 | 0xFA / 0x12 / 结果 / 数据地址(4) / 数据长度(4) |
| 终止读写请求 | 0xF9 / 0x13 / CRC16(2，高字节在前) |
| 终止读写响应 | 0xFA / 0x13 / 结果 / CRC16(2) |
| 上行数据 | 0xFA / 0x14 / 包序列号(0x00~0xFF) / 有效长度 / 数据 |
| 下行数据 | 0xF9 / 0x14 / 包序列号 / 有效长度 / 数据 |
| 下行数据响应 | 0xFA / 0x18 / 包序列号 / 有效长度 |
| 终止数据传输 | 0xFA / 0x14 / 0x00 / 0x00 |
| 设置升级标志 | 0xF9 / 0x16 / 标志(4)：`0xF5F5F500` 有效，`0x00000000` 无效 |
| 获取升级标志 | 0xF9 / 0x15 → 0xFA / 0x15 / 状态 / 标志(4) |

结果码：`0x00` 成功；`0xF0` 失败（正处于读写流程）；`0xF2` 失败（不存在对应数据）。

### 3.5 数据类型取值

| 类型（8 字节 ASCII） | 含义 | 读 | 写 |
|---|---|---|---|
| `rel0` | 遥控器硬件信息 | ✓ | ✓ |
| `usr1` | 升级数据版本信息 | ✓ | ✓（E.3.5） |
| `usr2` | 认证识别码 | ✓ | — |
| `irtv` | 电视机红外遥控基础信息 | — | ✓ |
| `irstb` | 机顶盒红外遥控基础信息 | — | ✓ |
| ~~`bletv`~~ | ~~电视机蓝牙（星闪）遥控基础信息~~ | — | **不做**（电视机无蓝牙） |
| `blestb` | 机顶盒蓝牙（星闪）遥控基础信息 | — | ✓ |
| ~~`fw01`~~ | ~~固件~~ | — | **不做**（固件升级走 CAT1 UDP） |

## 四、认证（E.1.2，下载前强制）

### 4.1 算法

```
哈希值 = MD5( key || rand || idcode )
         key    16 字节
         rand   16 字节
         idcode 32 字节（定长，不足补 0）
```

### 4.2 双向流程

1. 遥控器生成 `rand1`，按 `key_index` 取 key，算 `uc_rand_hash1`；
2. 遥控器发「升级主机认证请求」，状态码 `0x00`，带 `key_index`、`rand1`、`idcode`；
3. 主机用同样参数算 `uh_rand_hash1`，通过「响应」回传；
4. 遥控器比对（**不区分大小写**）：一致 → 发状态 `0x01`（通过）；不一致 → 发状态 `0x02`（失败，流程结束）；
5. 主机生成 `rand2`，发「遥控器认证请求」，状态码 `0x00`；
6. 遥控器算 `uc_rand_hash2` 回传；
7. 主机比对：一致 → 发状态 `0x01`；不一致 → 发状态 `0x02`，流程结束。

### 4.3 前置条件

- 遥控器固件需**预置 idcode（32 字节）**和**至少一组 key（16 字节）**；
- APP 侧需内置**同一套** idcode/key，否则无法算出相同哈希；
- 需支持多组密钥（`key_index` 从 0 开始），便于后续换密钥。

## 五、下载主流程（E.3）

```
a. APP 与遥控器建立蓝牙连接
b. 双向认证通过（E.1.2）
c. 读遥控器硬件信息（rel0）→ 取 idcode
d. 读升级数据版本信息（usr1）→ 判断是否需要下载
e. 设置升级标志 = 0xF5F5F500（有效）
f. 启动写请求（指定 irtv / irstb / blestb 之一）
g. 下行数据传输（分包写入）
h. 传输完成后，主机算 CRC1，遥控器算 CRC2
i. 遥控器发「终止数据传输」
j. 主机发「终止读写请求 + CRC1」
k. 遥控器比对 CRC1 与 CRC2：不一致 → 失败结束；一致 → 「终止读写响应 + CRC2」
l. 主机再比对一次 CRC1 与 CRC2
m. 成功后写新的版本信息（E.3.5），再设置升级标志 = 0x00000000（无效）
```

### 5.1 读取硬件信息（E.3.2）

返回文本，`key:value` 格式，多组换行分隔：

```
idcode:<32 字节认证识别码>
```

### 5.2 读取/写入版本信息（E.3.3 / E.3.5）

数据格式：`CRC16(2) + 长度(2) + 数据体`，**低字节高位**字节序（即高字节在前）。

数据体字段：

| 字段 | 含义 |
|---|---|
| `fw` | 固件版本 |
| `tbi` | 电视机品牌 id |
| `tmi` | 电视机型号 id |
| `sbi` | 机顶盒品牌 id |
| `smi` | 机顶盒型号 id |
| `irtv` | 电视机红外基础信息版本 |
| `irstb` | 机顶盒红外基础信息版本 |
| `bletv` | 电视机蓝牙基础信息版本（**本方案不使用，恒为默认值**） |
| `blestb` | 机顶盒蓝牙基础信息版本 |

> 写入流程（E.3.5）：启动写 → 下行传输 → 下行响应 → 「数据传输完毕请求」→ 遥控器发终止读写请求 → 主机回终止读写响应。

### 5.3 约束

- **不支持断点续传**（E.3.1 明文），中断即整包重来；
- 一次下载只处理一种数据类型（`irtv` / `irstb` / `blestb` 之一），三套键值分别独立下载、独立校验、独立生效；
- CRC 不通过时整包丢弃，**旧值必须保留**；
- 收到 `bletv` 类型的下载请求应返回失败（`0xF2` 不存在对应数据），避免 APP 侧误下发。

## 六、红外键值文件格式（E.3.6.1 / 表 E.24）

### 6.1 结构

```
文件头
  tag            4   固定 "ETV\0"（45 54 56 00）
  spec_version   2   初始版本 0x0001
  reserved       6   0x000000000000
  file_version   4   文件版本
  file_size      4   完整长度（从 tag 开始算）

全局参数
  freq_ratio     1   高 4bit 载波，低 4bit 占空比
  data_set_flag  1   bit6 = has_tension，bit7 = has_key_map
  scale          1   时长缩放倍数
  table_num      1   协议数量 TN
  key_num        2   按键数量 KN
  repeat_mode    1   0=AAAA / 1=ABBB / 2=ABAB
  reserved       1
  enc            1   1=PW 编码，2=BP 编码

协议表 × TN
  enc / unit(2) / has_start / has_toggle_bit / data_bit_num / header2_pos / col_num
  b0(4) / b1(4) / b2(4) / b3(4) / header(4) / header2(4)

列表 × CN
  bit_num / ref_col_index / has_header / burst(4)

按键表 × KN
  key_id(2) / table_index(1) / key_value(8)

按键映射表（has_key_map 时）
  key num / (key_no, key_id2)

扩展区（has_tension 时）
  extension_len(4) / extension_data
```

**全文件大端排序。**

### 6.2 编码规则要点

| 字段 | 规则 |
|---|---|
| `freq_ratio` 高 4bit | 1=36k, 2=37k, 3=38k, 4=39k, 5=40k, 6=56k |
| `freq_ratio` 低 4bit | 1=1/2, 2=1/3, 3=1/4, 4=1/5 |
| `scale` | 所有时长超 65535 时整体除以 scale，发码时乘回 |
| `b2`/`b3` 同时为 0 | 按 1 bit 一组：0→b0，1→b1 |
| `b2`/`b3` 同时非 0 | 按 2 bit 一组：00→b0，01→b1，10→b2，11→b3 |
| `bit_num` | `key_value` 的有效位数，**低字节低位**起始 |
| `ref_col_index` | 允许引用其他列的数据编码（见附录 I.3 示例） |
| `burst` 全 0 | 结束码无效 |
| `burst[0]>0, burst[1]=0` | 结束码为低电平 |
| `repeat_mode` | 0=AAAA（无重复码，重发键码）；1=ABBB；2=ABAB |
| `key_id = 1002` | **固定为重复码 ID** |
| 带重复码时 | 默认所有按键共用同一重复码 |

### 6.3 编码流程

```
按键键值 → 转二进制 → 按 bit_num 取有效位
   → 1 位一组 或 2 位一组（取决于 b2/b3）
   → 逐组替换为 b0~b3 的高低电平时长
   → 头部加 header，尾部加 burst
   → 按 freq_ratio 载波输出
```

### 6.4 两种编码协议

- **PW 编码**（`enc = 1`，脉宽调制）：附录 I.1 有完整示例
- **BP 编码**（`enc = 2`，双相编码）：附录 I.2 有完整示例；额外用到 `unit`、`has_start`、`has_toggle_bit`

**两种都必须实现**，否则遇到另一种编码的电视就编不出波形。

## 七、蓝牙键值文件格式（E.3.6.2 / 表 E.25）

> 本方案中该格式**只用于 `blestb`（机顶盒蓝牙）**。电视机侧无蓝牙，文件中即便带有电视机条目也应跳过。

### 7.1 结构

```
文件头
  name(64)  version(64)  size(32)  CRC32(32)  reserved(64)

device_nums(32)  version(64)

设备索引表 × device_nums
  device_type(32)  device_id(32)  device_detail_offset(32)  device_detail_size(32)

设备详情 × device_nums
  广播参数（配对 / 回连 / 开机 三套）
      xxx_adv_length(5bit) + xxx_adv_power_level(3bit)
      + xxx_adv(8×31) + xxx_dur_ms(16) + xxx_interval_ms(16)
  spec_adv_mac_enable / type / addr(48)
  scanrsp_adv_length(8) + scanrsp_adv(8×31)

  fc2hid_entry_count(8, ≤48)
     key_fcode(16)  key_usage_page(8)  key_modifier(8)  key_usage_id(16)  reserved(16)

  fc2no_entry_count(8, ≤48)
     key_fcode2(16)  key_no(8)

  VID(32)  PID(32)
```

### 7.2 映射表含义

| 表 | 作用 |
|---|---|
| `fc2hid` | **按键功能代码 → HID 键值**：`key_usage_page` + `key_modifier` + `key_usage_id` |
| `fc2no` | **按键功能代码 → 表 B.1 按键功能序号**（1=电源、2=直播业务、18=频道+ …） |

### 7.3 关键规则

| 项 | 规则 |
|---|---|
| `device_type` | `0x00000000~0x7FFFFFFF` = **电视机**；`0x80000000` 及以上 = **机顶盒**。本方案**只接受机顶盒条目**，遇到电视条目应跳过并记日志 |
| `device_nums` | 文件可含**多个设备**（对应 APP 中选择品牌型号） |
| `key_usage_page = 0x07` | 键盘页：`key_usage_id` 最多 2 个按键，**各占 1 字节** |
| `key_usage_page = 0x0C` | 消费类页：1 个按键，**占 2 字节，大端** |
| `key_modifier` | bit0~3 = 左 Ctrl/Shift/Alt/GUI，bit4~7 = 右 Ctrl/Shift/Alt/GUI |
| `key_no` | 直接引用表 B.1 的功能序号 |
| `VID` / `PID` | 接收设备的厂商 ID 与产品 ID |
| 上限 | `fc2hid` 与 `fc2no` 各最多 48 项 |

## 八、写指令配置（E.1.1.3.19，操作码 0x22）

这是下载协议里**容易被忽略但很关键**的一环，直接决定按键路由：

| 指令码 | 内容 | 取值 |
|---|---|---|
| `0x01` | 设置控制目标 | `1` = 电视机和机顶盒；`2` = 电视机开关机和机顶盒；`3` = 仅机顶盒；`4` = 仅电视机 |
| `0x02` | 设置电视机进入直播信源按键的方式 | byte1 = 按键间隔（×100 ms）；byte2 = 按键个数；byte3~N = **表 B.1 按键功能序号** |

**含义：双控的目标组合和“切到直播信源”的按键序列，是可以通过下载配置下发的，不必写死在固件里。** 这一点把“双控”与“下载键值”两项需求连起来了。

## 九、校验算法（附录 J）

| 算法 | 用途 | 参数 |
|---|---|---|
| CRC16 | 终止读写请求的传输校验 | 多项式 `x16+x12+x5+1`（代码体现为 `0xA001` 反转式） |
| CRC32 | 蓝牙键值文件头校验 | 反转式，多项式 `0xEDB88320` |
| MD5 | 认证摘要 | 见 E.1.2 |

**注意**：现有 OTA 用的 CRC 参数需与附录 J 逐项核对，不能想当然认为一致。

## 十、固件侧落地设计

### 10.1 存储结构

```
ROM（随固件烧写，永不被下载改写）
  └─ 出厂默认表
       ├─ 三套键值数组（机顶盒蓝牙 / 机顶盒红外 / 电视机红外）
       └─ 红外协议描述表（载波、位格式、header、burst）

Flash（独立扇区，约 1~2 KB）
  └─ 下载覆盖层
       ├─ 记录：{ 类型, 键号/表索引, 值 }
       ├─ 每套独立版本号
       └─ CRC + 提交标志
```

### 10.2 查表优先级

```
学习值（带序号） > 下载值（带版本） > 出厂默认值
```

依据 7.4“键值以最后更新的为准”，**必须通过时间戳/序号判断新旧**，不能简单让学习值永久优先。

### 10.3 恢复出厂

现有“主页 + 音量- 3 秒 → 10 秒内按确认”流程已在清除学习数据与用户码，追加“擦除下载覆盖层”即可，擦除后自然回到 ROM 默认值。

### 10.4 时序约束

- 下载写 Flash 期间禁止红外收发与学习，复用现有 `udp_ota_session_busy()` 互斥机制；
- 所有 Flash 访问放在任务上下文，不在中断内进行；
- 下载期间禁止进入待机/休眠。

### 10.5 空间约束

| 项目 | 余量 | 说明 |
|---|---|---|
| Flash（APP1 代码区） | 约 14 KB | **不足**，需先调整分区 |
| Flash（数据区） | 60 KB 未分配（0x01071000~0x0107FFFF） | 存放覆盖层充裕 |
| RAM | 约 288 字节 | 表不宜常驻内存，建议按键时按需读取 |

### 10.6 与现有代码的对应关系

| 规范要求 | 现状 | 处理 |
|---|---|---|
| 表 A.5 升级服务 | 无 | 新增 GATT 服务与特征 |
| 20 个接口解析 | OTA 有帧校验经验可参考 | 新增命令状态机 |
| MD5 认证 | 现有 AES，无 MD5 | 按附录 J 新增 |
| 红外键值文件解析 | 只会 RC6（`ir_rc6_encode.c`）与 NEC（`irc.c`） | 新增 ETV 解析 + PW/BP 编码 |
| 蓝牙键值映射 | `ble_hid_kbd.c` 为编译期 switch | 改为查表 |
| 表 B.1 按键序号 | 无 | 建立序号 ↔ 物理键映射 |
| 键值落盘 | 无 | 新增 Flash 分区 |
| 恢复出厂 | 已清学习数据与用户码 | 追加清覆盖层 |

## 十一、需客户提供的前置资料

| # | 资料 | 阻塞内容 |
|---|---|---|
| 1 | **idcode（32 字节）+ 至少一组 key（16 字节）** | 认证无法实现，整个下载流程走不通 |
| 2 | **附录 I 对应的真实键值文件样本**（PW 与 BP 各一份） | 解析器无法自测验证 |
| 3 | “通用遥控”APP 实现方及联调接口人 | 联调 |
| 4 | 确认 `bletv`（电视机蓝牙）确实不做，APP 侧不下发该类型 | 文件解析范围 |
| 5 | 机顶盒侧是否也需参与（7.4 中机顶盒为“宜支持”） | 是否需要对方配合 |

## 十二、工作量参考

| 工作项 | 人日 |
|---|---|
| 升级服务 + 20 个接口状态机 | 10 |
| 认证（MD5 + 密钥管理） | 4 |
| 读取硬件信息 / 版本信息，写入版本信息 | 5 |

| 蓝牙键值文件解析 + 映射表（仅 `blestb`） | 6 |
| 写指令配置（控制目标 / 直播信源） | 3 |

> 相比含电视蓝牙的方案（约 60 人日）减少约 4 人日，主要省在蓝牙文件解析只服务机顶盒一套、联调少了电视侧配对场景。
> 软件整体口径不变：约 2 个月（2 人并行）。

## 十三、主要风险

| # | 风险 | 应对 |
|---|---|---|
| 1 | 键值文件格式复杂（PW/BP 双编码、列复用、扩展区） | 要求客户提供真实样本，先做解析器单元测试 |
| 2 | 认证密钥未提供 | 冻结为开发前置条件 |
| 3 | APP1 代码区仅剩 14 KB | 立项前先定分区调整方案 |
| 4 | 机顶盒蓝牙键值受现有 HID 报告描述符限制（消费类仅 3 个 usage） | 如需扩展需同步修改描述符，并与机顶盒侧确认兼容 |
| 5 | 不支持断点续传，传输中断需整包重来 | 下载包不宜过大，做好超时与重试提示 |
| 6 | 规范 7.2 c) 要求“长按音量- + 电视机业务 3s 发起与电视机配对”，而电视机无蓝牙，该流程无法完整执行 | **需与规划院书面确认口径**：可保留组合键并发送配对请求红外码 0x7D，但无后续蓝牙连接；争取在符合性测试中列为“不适用” |
