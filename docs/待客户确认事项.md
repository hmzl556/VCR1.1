## Q1 需要真实的 `irtv` / `irstb` 键值文件样本

- **要什么**：规划院"通用遥控"APP 实际下发给遥控器的那个二进制文件，电视机和机顶盒各一份（几百字节到几 KB）。
- **为什么**：规格书附录 I 只有节选的格式示例。解析器必须用真实文件验证，否则只是"按我的理解自说自话"。
- **我方临时处理**：按表 E.24 自建符合规范的文件做主机测试（见 `tools/tests/test_upg_flow.c` 的 ETV 用例），真实文件到了只需补一个回归用例。
- **风险**：如果真实文件有规范未写清的约定（多列、扩展区、映射表），解析结果会错，且要到上板才能发现。
- **2026-11-25 进展**：已用规划院「通用遥控」APP（`cn.abp2023.ykqxxk.gd`）+ 固件 `UPG_DEBUG_DUMP` 抓包，拿到电视 `irtv` 真实文件 **501 字节**（海信 / 型号「通用」）。
  - 实际参数：`spec_version = 4`、`scale = 2`、`table_num = 2`、`key_num = 27`、`repeat_mode = 1`（ABBB）、`ratio_freq = 0x32`（38 kHz / 1:3）
  - 协议表 0 为标准 NEC（×scale 2 后 9000/4500、560/560、560/1680），协议表 1 是双列重复码表
  - **文件末尾带 30 条按键映射表**（`key_no → key_id`），映射表不受 `data_set_flag` bit7 控制（见 Q11）
  - 已做成回归用例 `etv_real_case()`（`tools/tests/test_upg_flow.c`），样本数据内嵌
  - **仍缺 `irstb`（机顶盒红外）真实样本**，请 APP 选机顶盒品牌型号时再抓一份

## Q2 ETV 样本 `file_size` 与结构算出来对不上

- **现象**：附录 I 表 I.1（PW 示例）声明 `key_num = 33`、`file_size = 512`，但按表 E.24 逐字段累加：
  - 文件头 28 字节 + 1 个协议表 39 字节（`col_num = 1`）+ 33×11 字节按键 = **430 字节**
  - 与 512 差 82 字节。
- **请确认**：是样本节选/`file_size` 仅为示意，还是结构里还有未列出的字段（如填充、重复码条目、协议表尾部保留）。
- **我方临时处理**：解析器**按结构顺序遍历，不依赖 `file_size` 判断结尾**，并在每步做越界检查。
- **2026-11-25 结论**：真实文件 `file_size = 501`，按结构累加正好 501（28 + 39 + 46 + 27×11 + 1 + 30×3），**完全自洽**。附录 I 表 I.1 的 512 应是节选/示意。此项可关闭。

## Q3 认证密钥 `idcode` / `key` 的真实值

- **要什么**：附录 J 所述的一组认证密钥（`idcode` 32 字节、`key` 16 字节），以及是否需要多组。
- **为什么**：现在固件用开发占位值 `VCR1DEVIDCODE000…` / `VCR1DEVKEY000000`，日志会打 `warning: dev auth key in use`。

## Q4 认证是否强制

- **规格原文**：E.1.2「应在与升级主机建立连接后，进行遥控基础信息下载或固件升级之前，与升级主机进行认证」——是强制语义。
- **请确认**：机顶盒/APP 侧实际是否会走完整双向认证（`FA 20` → `F9 20` → `F9 21` → `FA 21`）。
- **我方临时处理**：`UPG_REQUIRE_AUTH = 0`，不认证也能下载，便于联调。
- **量产红线**：需改成 1，且产测先写密钥。
- **2026-11-25 实测**：「通用遥控」APP 全程**未发 `0x20` / `0x21`**，连上后直接读 `usr1`、写 `irtv`。
  - 说明 APP 侧当前不走认证；但我们发的 `FA 11 ...`（认证启动）它也不报错，属于忽略
  - **仍需确认**：正式机顶盒（而非手机 APP）是否会走认证。若会，`UPG_REQUIRE_AUTH` 必须置 1 并写入真实密钥（Q3）

## Q5 `usr1` 前 4 字节的字节序

- **规格原文**：表 E.23 中 CRC16 与长度都写「低字节高位的字节序」，措辞含糊；表 E.7 的 CRC16 则明确「高 8 位在前」。
- **我方实现**：按「高字节在前」（`crc>>8`, `crc&0xFF`）。
- **请确认**：拿机顶盒实际报文核对一次；若相反，改动只在 `upg_meta_build_usr1()` 一处。
- **2026-11-25 结论**：APP 写 `usr1` 的 100 字节内容开头正是 `A0 CC 00 60`，随后它发 `F9 13 A0 CC` 终止——**CRC16 就取前 2 字节，大端**；`00 60` 是长度 96。我方现有实现正确，此项可关闭。
  - 顺带确认 `usr1` 正文是 `key:value\0\n` 文本：`fw:02020000` / `tbi:1508` / `tmi:1103` / `sbi:0` / `smi:0` / `irtv:alpha-v1.0.101` / `irstb:0` / `bletv:0` / `blestb:0`。我方只做透传存储，不需要解析。

## Q6 规格 E.3.5「更新版本信息」的终止读写方向

- **矛盾点**：E.3.4（基础信息下载）是**主机**发 `F9 13` 终止读写、遥控器回 `FA 13`；E.3.5（更新版本信息）却写成**遥控器**发终止读写请求、主机回响应。而表 E.6 把 `0x13` 定义为「主机→遥控器」。
- **我方判断**：按 E.3.5 为笔误处理，主方向与 E.3.4 一致。
- **请确认**：机顶盒侧实际行为，避免双向都试造成超时。
- **2026-11-25 结论**：APP 全程都是**主机（APP）发 `F9 13`**、遥控器回 `FA 13`，包括写 `usr1` 之后。我方按 E.3.4 方向实现正确，此项可关闭。

## Q10 「学习值」与「下载值」的优先级口径

- **背景**：规范 7.4 要求"键值以最后更新的为准"。学习值存在波形区（自带写序号 `s_sequence`），下载值存在覆盖层（记录自带 `seq`），**两个序号是各自独立的计数器，不在同一时间轴上**。
- **我方实现**：`ir_send_key()` 比较两个序号取较大者；序号相同（例如都是 1）时**学习值优先**，因为那是用户当面的显式操作。
- **请确认**：这个近似口径是否可接受。若要严格语义，需引入统一的"最后更新时间戳"，两层各多存 4 字节并同步维护（会改动波形区格式，需要迁移）。
- **影响**：只在"同一个键既有学习值又有下载值"时体现；其余情况无差别。

## Q11 ETV 的 `data_set_flag` bit7（有无映射表）与实际不符

- **规格原文**：表 E.24 规定 `data_set_flag` 的 bit7 为 `has_key_map`，为 1 表示后面带按键映射表；bit6 为 `has_tension` 表示带扩展区。
- **实际情况**：真实 `irtv`（501 B）的 `data_set_flag = 0x01`，**bit7 = 0、bit6 = 0**，但文件末尾确实有 30 条映射表（91 字节），而且不加这段就凑不满 `file_size = 501`。
- **我方处理**：`etv_open()` **不再看这个标志位**，改为按剩余字节结构判定——按键表之后的剩余长度不小于 `1 + n×3` 时，把首字节当条目数。这样对两种写法都兼容。
- **请确认**：这是 APP 侧实现的 bug，还是规范该位另有含义（例如只有"映射表与按键表不一致"时才置 1）。若后续版本修正了该位，我方实现不需要改。

## Q12 APP 在「红外+蓝牙」模式下被拒 `bletv` 后的行为

- **现象**：APP 里选「红外+蓝牙」类型时，除了下发 `irtv`（501 B），还要下发 `bletv`（753 B）。我方按 D1 回 `FA 12 F2`（类型不支持）。
  - 第一次实测：APP **卡在 35% 不再前进**，用户必须手动退出
  - 第二次实测：APP 自动**从头重试整轮**（重发 `F9 16` 置标志、重写 `irtv`），随后写 `usr1` 并清标志，最终显示"升级成功"
- **我方判断**：APP 侧对 `F2` 的错误处理不完善（重试而不是提示）。**功能本身没问题**——`usr1` 里 APP 自己写的是 `bletv:0`，说明它接受了我们没有电视蓝牙键值。
- **建议反馈规划院**：
  1. 收到 `FA 12 F2` 后应直接提示"该遥控器不支持该类型"，而不是重试整轮（多耗一轮 BLE + 一次 Flash 擦写）；
  2. 或者把「仅红外」做成显式选项，避免用户选错。
- **对客户的影响**：无。只是联调体验问题。

1. 在「状态一览」加一行（编号顺延）；
2. 下面加一节，写清**要什么 / 为什么 / 我方临时处理 / 风险或红线**；
3. 客户回复后把状态改成「已确认」，并在该节末尾追加：`YYYY-MM-DD 客户回复：…（结论）`。
