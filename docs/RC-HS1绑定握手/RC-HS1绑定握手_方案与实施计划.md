# 蓝牙芯片 ↔ 4G 模组 绑定握手（RC-HS1）实施方案

## 1. 问题与目标

现状：蓝牙芯片（BR1601x）通过 USART1 以 AT 指令驱动 CAT1 模组（NT26 方案 B，`AT+ECSO*`），
两者是两颗独立固件，**没有任何互认机制**——任意一方换成第三方固件/克隆板都能工作。

目标：定义一条私有 AT 指令，由蓝牙芯片发起随机挑战、模组做密钥化的数据扰乱运算并回算，
蓝牙芯片本地校验，不通过则复位系统。从而把"我方蓝牙固件"与"我方模组固件（含密钥）"绑定。

威胁模型（**防**）：克隆模组、用廉价模组配我方蓝牙固件、把模组换成"哑终端"。
威胁模型（**不防**，需另立手段）：Flash 读保护被攻破后整包固件 dump、物理提取密钥。
缓解建议：密钥放产测可写的独立扇区（非 ROM）+ 至少按批次换密钥 + `idx` 预留每台唯一。

## 2. 方案总览

```
冷启动 ──► 模组上电(LTE_EN) ──► boot 2s ──► 波特率同步(AT/AT+IPR) ──► AT+RCHS=0,<nonce>
                                                                          │
                          出错/超时/响应不匹配 ◄──────────────────────────┤
                                  │ 3 次(换 nonce)                        │ 匹配
                                  ▼                                       ▼
                        复位 / 锁定(见 §5)                        置"可信"标志
                                                                          │
             每次模组上电 + 运行中不定期(2~10min 随机) 重新挑战 ◄────────────┘
```

算法与报文规范见 `RC-HS1绑定握手_技术需求书_v1.md`；参考实现 `rchs_ref.c`
（已用 gcc 自测通过，包含 XTEA 官方向量与 5 组协议向量）。

### 2.1 算法（已定稿，待讨论细节）
- `resp = XTEA_encrypt_32cycles(K[16], nonce[8])`，64-bit 分组 / 128-bit 密钥 / 32 cycles / 全大端。
- 挑战 8 字节随机，应答 8 字节；`AT+RCHS=<idx>,<nonce16hex>` → `+RCHS: <resp16hex>` + `OK`。
- 另设 `AT+RCHS?` → `+RCHS: 1,<kcv8>`，用于产测核对两边密钥一致 + 固件兼容性探测。
- 选择 XTEA 而非自研扰乱函数的理由：有官方测试向量可交叉验证，两边实现不会"各写各的"；
  代码 ~20 行、无查表、RAM < 32B、M0 @12~64MHz 单次 10~100 µs。

### 3.1 关键约束（已核对现有代码）
- **模组平时是断电的**（`rc_cat1_power_down()`：`LTE_EN_OFF()`；有业务才上电）。
  因此"不定期握手"只在模组本来就上电时做，**不额外上电**，零功耗代价；
  冷启动必做一次握手，需给模组一次上电（+2~3 s 启动时间）。
- 所有 AT 走 `cat1_modem_begin_wait()` / `cat1_modem_step()` 事务机，握手必须是新 phase，
  不能自己收发字节，否则 `+ECSONMI`/ECSORF 状态机会失步。
- 应答解析：`s_modem_rsp`（128 B）已能容纳 `+RCHS: xxxxxxxx`；用 `+RCHS:`（冒号）区分
  `ATE1` 回显行 `AT+RCHS=`。
- IWDG 10 s：模组 boot 2 s + 波特率同步约 1 s，门禁期间需保持喂狗。

## 4. nonce 生成（防重放的关键）

芯片没有硬件随机数发生器（SDK 未提供），采用"软件伪随机 + 密钥派生"三层构造：

```
种子(摆骰子) -> xorshift128 状态 -> nonce = XTEA(K, ctr||rng) -> 拒绝全0/重复
                                            ^
                    成功握手后: rng ^= resp ^ now_ms  (回灌)
```

1. **种子**：`SystemGetMacAddr()/SystemGetUUID()`（芯片唯一号）+ 首次调用时 `sdk_timer_get_current_ms()`
   （开机时序抖动）+ ADC 采样低位噪声（可用则用）+ 产测 `idcode`。
2. **派生**：`nonce = XTEA(K, counter_be32 || rng32)`，counter 自增。
   即使攻击者知道种子，**没有密钥也推不出下一个 nonce** —— 这是纯 xorshift 做不到的。
3. **回灌**：每次握手成功后 `rng ^= resp ^ now_ms`，一次成功后彻底不可预测。
4. **约束**：拒绝全 0、拒绝与最近 8 个重复；复位后靠种子区分。
5. 模组侧无需关心生成方式，只需拒绝"与上一次相同"的 nonce。

## 5. 失败策略
一次"握手事件"= 最多 3 次尝试（每次换 nonce，300 ms 超时）。全失败：
1. `NVIC_SystemReset()`；
2. 若本次启动的复位原因已是"软件复位"（即上次正是因握手失败复位），启动握手再失败则进入
   **锁定态**：停广播/停按键上报/停红外，LED 3 短闪，保留 BLE 升级服务以便 OTA/产测恢复，
   不再复位（避免无限复位把电池耗干）；
3. 电池重新插拔（POR）后重新判定。

依赖 `RCC_CTRLSTS` 的 `SFTRSTF`/`PORRSTF`，无需 Flash 写计数（不磨损、不掉电写）。

## 6. 密钥与产测
- 蓝牙侧：`FLASH_AUTHKEY_START` 扇区新增 `module_key`，产测写入；空则用编译期开发密钥（联调可用，**量产红线**）。
- 模组侧：**按批次编进模组固件**（未出货，无需产测写密钥命令）；若日后要现场换密钥，再让利尔达加 `AT+RCHSK=<idx>,<key32hex>`。
- 双方各自算 KCV，产测台架用 `AT+RCHS?` 比对，不一致即报警。

## 9. 模组侧可行性（利尔达 NT26-FCN-C）

模组型号：**利尔达 NT26-FCN-C**，平台 = 紫光展锐 **EC718**（C 系列，对应 OpenCPU 包 `F6C_A`，如 `NT26FCNC00WNA`）。
现有 `AT+ECSOCL/ECSOCR/ECSONMI/ECSOST/ECSORF` 属展锐/利尔达 AT 集（非 3GPP 标准），
且利尔达官方文档 **《客制化AT 开发指导_Rev1.2》** 专门讲"如何添加自定义 AT 指令"
（`LIOT_AT_CMD_SET/READ/TEST/EXE`、`liot_atHandle`、`args_count`、`liot_at_register` 等），
⇒ **加一条私有 AT 指令是有官方支持的标准做法，不是特殊需求。**

| 路径 | 谁做 | 优点 | 代价/风险 |
|---|---|---|---|
| **A. 标准 AT 固件加指令** | 利尔达 | 我们零改动、零维护 | 等排期；密钥/算法细节要他们实现（有参考代码） |
| **B. OpenCPU SDK 自研** | 我们 | 不依赖排期，密钥与算法全在手里 | 接管模组固件（编译/烧录/回归），后续不能直接跟利尔达 AT 升级；需申请 OpenCPU 与烧录授权 |

**建议**：先按 A 报价/排期；同时向利尔达要 OpenCPU SDK + 烧录授权作为 B 的备选。
两条路下**我们的蓝牙侧改动完全一样**。

密钥存放（任一即可）：编进模组固件（按批次）/ OpenCPU 预置配置区 PRECFG / 模组文件系统。
未出货 ⇒ 不需要产测写密钥命令，按批次编进固件最省事。

**问利尔达的三句话**
1. NT26-FCN-C 的标准 AT 固件能否加一条私有指令 `AT+RCHS`（含 `AT+RCHS?`），周期与费用？
2. 若我们自己做：C 系列对应的 OpenCPU SDK 包（资料中为 `F6C_A`）+《客制化AT 开发指导》+ 烧录授权能否提供？OpenCPU 固件里 EC AT 指令集是否完整保留？
3. 模组固件版本查询指令（`ATI`/`AT+GMR`）是什么？便于我们按版本决定是否强制。

**验收（模组侧完工标准）**
1. `AT+RCHS?` 回 `+RCHS: 1,50D38D93`（测试密钥）；
2. 5 组协议向量全对；
3. 连续 100 次快速请求不丢包、不影响其它 AT 指令、不干扰 `+ECSONMI` URC。

### A.3 产测 SOP（密钥一致性检查）

1. 给待检遥控器上电，串口接模组 UART；
2. 向模组发 `AT+RCHS?`，记录返回的 KCV（如 `50D38D93`）；
3. 用同一批次的密钥在 PC 上算 KCV（或读蓝牙侧打印的 KCV）；
4. 两者一致 → 通过；不一致 → 报警：该台蓝牙固件与模组固件不是同一批次密钥。

**台账要求**：模组固件版本号 ↔ 批次 ↔ 密钥（16 字节 hex）↔ 蓝牙固件版本，一一对应留档。
