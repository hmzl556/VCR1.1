# GY/T 407-2024 键值下载 —— RAM 与存储约束定稿

> **文档定位**：解决《GYT407按键键值下载-本固件实现方案.md》第十章遗留的 RAM 硬约束（原冲突 C2）。
> 结论：**Flash 已解决，RAM 通过「独占会话 + 借用现有缓冲」实现零新增静态占用。**
>
> 本文所有数字均来自实测（Keil map、datasheet、源码调用链），不含估算。

## 一、SRAM 定案

| 项目 | 结论 | 依据 |

> 此前 `ble_dtss.uvprojx` 里写的是通用模板 `IRAM(0x20000000, 0x20000)`（128 KB），
> 与 datasheet 不符，**以 datasheet 的 48 KB 为准**。

## 二、48 KB 精确账本（无隐性余量）

| 区域 | 起始 | 上限 | 已用 | 余量 |
|---|---|---|---|---|
| cs.lib BLE 协议栈预留 | 0x20000000 | 7,168 | 未验证 | — |
| RW_IRAM0（语音 / AES / qflash / PCM DMA） | 0x20001C00 | 9,216 | 9,156（0x23C4） | **60** |
| RW_IRAM1（应用数据） | 0x20004000 | 31,712 | 31,688（0x7BC8） | **24** |
| 故障记录 | 0x2000BBE0 | 32 | 32 | 0 |
| 主栈 / 中断栈 | 0x2000BC00 | 1,024 | 1,024（0x400） | **0** |
| **合计** | | **49,152** | **49,152** | **84 B** |

### 2.1 为什么没有隐性余量

SDK 参考工程的 scatter（`VCR-新板红外发送与自学习/demo/ble/ble_dtss_cgm/prj/ble_dtss.sct`、
`BR1601x_SDK_LOW_POWER_demo/.../dat.sct`）原本是：

```
RW_IRAM0 0x20001C00 0x00001C00   ← 7 KB，止于 0x20003800
                                  ← 0x20003800–0x20004000 留 2 KB 空隙
RW_IRAM1 0x20004000 0x00008000   ← 32 KB
```

**本项目把 RW_IRAM0 从 7 KB 扩到 9 KB（0x2400），这 2 KB 空隙已经被吃掉了。**
所以现在没有可回收的碎片空间。

### 2.2 不能动的两块堆

| 堆 | 大小 | 说明 |
|---|---|---|
| FreeRTOS heap_4 | **768 B** | `configTOTAL_HEAP_SIZE`，本身已很小 |
| 标准 C 堆 | **8 KB**（`Heap_Size 0x2000`） | `app_heap.h` 注明 `brt_malloc` 共享 SDK 的这块堆，**正在使用中**，不能随手砍 |

> 备注：旧板基础曾用 10 KB，本项目已压到 8 KB。再压会引入堆耗尽的运行期风险，
> 所有 `app_heap_alloc` 调用点虽都检查 NULL，但会退化为功能不可用，不建议。

## 三、三个可借用缓冲（map 实测）

| 模块 | 实测 ZI | 构成 | 占用窗口 | 借用可行性 |
|---|---|---|---|---|
| `aes_transport.o` | **784 B** | `s_aes_work[608]` + AES 轮密钥 176 | 一次加/解密调用内，指针不外泄 | 短时，可借 |
| `rc_cat1_bridge.o` | **608 B** | `s_cat1_tlv[608]` UDP PDU | 一次 CAT1 收发事务 | CAT1 阻塞时可独占 |
| `udp_bootload.o` | **512 B** | `s_flash_wr_buf[512]` | **跨调用持有**（stage→commit） | 需与 OTA 互斥 |

### 3.1 上下文安全性（已逐项核实）

- 全部 `IRQHandler` 已检查：`USART1_CAT1_IRQHandler` / `USART2_CAT1_IRQHandler` 只做接收入环形缓冲，
  **不调用** `remote_handle_downlink_frame`、`remote_report_poll`。
- AES 两个入口均在任务上下文：
  - `remote_reports.c:676` 解密 ← `remote_handle_downlink_frame` ← `rc_cat1_poll_downlink`
  - `remote_reports.c:746` 加密 ← `remote_report_poll` ← `rc_cat1_bridge` 轮询

✅ 因此「共享 + 独占锁」不会造成中断内等锁的死局。

## 四、方案：键值下载 = 独占会话，零新增静态 RAM

### 4.1 核心思路

复用现有 `udp_ota_session_busy()` 那套互斥语义（它已经能取消红外、退出学习、阻止休眠），
把键值下载定义成**第三种独占会话**：

```
进入下载 → 取得独占锁（禁 IR 收发 / 退学习 / 禁休眠 / 停 CAT1 事务 / 停 OTA）
        → 借用 s_cat1_tlv[608] 作为本会话工作区
        → 认证 → 读信息 → 收文件 → 写 Flash → 写版本 → 释放锁
```

因为锁在**整个会话期间**持有，`s_cat1_tlv` 全程归下载模块独占，可以放心当作持久工作区。

### 4.2 工作区分配（全部落在 608 B 内）

| 用途 | 字节 |
|---|---|
| GATT 收包缓冲（同时复用为 notify 组包） | 140 |
| 状态机 / 包序号 / 标志 | 40 |
| MD5 上下文 + 摘要 | 96 |
| 认证临时（rand / hash / idcode 分块） | 64 |
| 版本信息缓存（9 字段） | 80 |
| ETV 协议表（流式解析，只留当前表） | 约 200 |
| 波形合成（**流式**，不生成整帧 `ir_raw_t`） | 约 60 |

### 4.3 各阶段峰值

| 阶段 | 占用 | 是否 ≤608 B |
|---|---|---|
| 双向认证 | 340 B | ✅ |
| 读硬件信息 / 读版本 | 260 B | ✅ |
| 写键值 + ETV 解析 + 波形合成 | **440 B（峰值）** | ✅ |

**结论：峰值 440 B < 608 B，单个缓冲足够，`s_aes_work` 与 `s_flash_wr_buf` 无需借用。**

### 4.4 波形必须流式生成

**不要**沿用 `ir_rc6_send_wave()` 那套「先给一整帧 `ir_raw_t`（522 B）、内部再拷贝一份」的路径。
改为编码器按段产出、发送驱动按段取用的流式接口，峰值降到几十字节。

这也是本方案能把峰值压到 440 B 的关键。

## 五、代价与约束

### 5.1 唯一的代价：下载期间 CAT1 阻塞

| 影响项 | 评估 |
|---|---|
| 服务器心跳（周期 1800 s） | 错过一次无影响，下次照常 |
| Tag10 按键上报 | 用户正在下载，不会同时按键；且上报本身有队列缓冲 |
| 云端策略（Tag11）下发 | 延后处理，不影响功能 |
| CAT1 串口接收 | 仍由 ISR 进环形缓冲（`cat1_usart1` ZI 1,520 B），短时阻塞不丢 |
| OTA | 与下载互斥，二者不会同时进行 |

**已获确认：可以接受。** 但实施时应保证单次下载会话时长可控（目标 ≤30 s）。

### 5.2 硬性约束（实施时不得违反）

1. **锁必须在会话全程持有**，不能中途释放再重新获取（否则工作区内容会丢）；
2. **不得跨会话持有**借用缓冲，会话结束立即归还；
3. **回调里只收帧**，解析 / Flash 写入 / MD5 全部在任务上下文；
4. **不得在 ISR 中调用下载模块的任何函数**；
5. 会话期间禁止进入待机/休眠（沿用现有互斥判据）。

## 七、验证方法

### 7.1 编译期

- 确认新增静态 RAM ≈ 0：对比改动前后 `RW_IRAM1` 的 `Size` 与 `End`，允许 ≤32 B 增长
- `tools/build.ps1` 的 `RW_IRAM1 end ≤ 0x2000BBE0` 检查继续生效

### 7.2 主机测试（在现有 23 组基础上扩展）

- 会话独占：下载期间 IR 发送被拒、学习被拒、OTA 被拒、休眠被拒
- 工作区边界：峰值使用不得超过 608 B（编译期 `static_assert` 或运行时断言）
- 会话异常退出（CRC 失败、超时、断连）时锁必须释放
- 会话结束后 CAT1 事务能正常恢复

### 7.3 上板验证

- 下载全程 CAT1 心跳是否按预期延后、恢复后是否补发
- 下载期间按按键，恢复后 Tag10 队列是否完整
- 连续 100 次下载后 RAM 是否有泄漏迹象（栈水位、堆剩余）
- 示波器确认波形流式生成的实际时序与整帧生成一致

## 八、结论

1. **SRAM 48 KB 已确认**，且已精确用满，无隐性余量可捡。
2. **不需要新增静态 RAM**：把下载做成独占会话，借用 `s_cat1_tlv[608]` 作工作区，峰值 440 B。
3. **唯一代价是下载期间 CAT1 阻塞**，影响可控，已确认接受。
4. **波形必须改流式生成**，这是把峰值压进 608 B 的前提，也是相对原方案最重要的实现调整。
5. Flash 与 RAM 两项硬约束**至此全部关闭**，可以进入 P1 编码阶段。
